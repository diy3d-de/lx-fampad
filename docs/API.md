# API (Phase 1a bis 1c: Konten, Anmeldung, Sync)

Stand: Phase 1c-4a (Sync-Kern mit Listen, Kalender: Termine, Teilnehmer, Ausnahmen, und Aufgaben mit Unteraufgaben; Konten und Anmeldung seit 1a/1b). Basis: `https://familie.lx-labs.dev/api/v1`, REST mit JSON (`Content-Type: application/json`). Der Sync (`POST /sync`) ist im Abschnitt „Sync“ beschrieben; Chat und Dateien kommen als weitere Entitäten dazu. Diese Beschreibung ist Markdown statt OpenAPI; die Validierung steckt in den Zod-Schemas in
`server/src/routes/` (jedes Objekt ist `strict`: unbekannte Felder führen zu `400`).

## Allgemeines

**Fehlerformat** (nie interne Meldungen, kein Stacktrace; Details nur im Server-Log):

```json
{ "error": "invalid_credentials", "message": "Die Anmeldedaten sind nicht korrekt." }
```

| Status | Bedeutung |
| --- | --- |
| 400 | ungültige Eingabe (`invalid_request`, generisch) oder fachlich abgelehnt (`invite_invalid`, `weak_password`, `challenge_invalid`, `invalid_code`, `registration_failed`) |
| 401 | nicht angemeldet (`unauthenticated`), Anmeldedaten falsch (`invalid_credentials`, immer dieselbe Antwort, egal ob das Konto existiert), `invalid_token` (Refresh), `step_up_failed` |
| 403 | `forbidden`, `csrf_invalid`, `origin_not_allowed`, `step_up_required`, `account_pending` |
| 404 | nicht gefunden (`not_found`, auch für Objekte einer fremden Familie) |
| 409 | Konflikt (`last_admin`, `last_credential`, `invite_not_open`, `registration_failed`, `no_passkey`, `passkey_exists`, `password_exists`, `no_password`, `not_pending`, `cannot_remove_self`, `device_mismatch`, ...) |
| 413 / 415 | Body zu groß (`payload_too_large`, beim Sync über 1 MB) / kein JSON (`unsupported_media_type`) |
| 426 | `update_required`: die Protokollversion des Clients ist zu alt (nur `/sync`); die App zeigt die Pflicht-Update-Seite |
| 429 | Rate-Limit (`rate_limited`) oder verzögerte Sperre nach Fehlversuchen (`too_many_attempts`, Header `Retry-After` in Sekunden) |
| 500 | `internal_error` (nie mit Details; die stehen nur im Server-Log) |
| 503 | `server_busy` (Passwort-Berechnung ausgelastet, Header `Retry-After`) oder `maintenance` (Wartungsmodus des Betreibers: schreibende Anfragen, Sync und neue Anmeldungen, `Retry-After: 60`, Zusatzfeld `maintenance: true`; siehe Abschnitt „Betrieb“) |

**Fehlercodes im Einzelnen** (`error` im Antwortkörper; die App zeigt nie den `message`-Text, sondern eigene deutsche Meldungen je Code):

| Code | Status | Wann |
| --- | --- | --- |
| `invalid_request` | 400 | Eingabe ungültig (Zod-Schema, unbekannte Felder, NUL/Surrogate) |
| `invite_invalid` | 400 | Einladung unbekannt, benutzt, widerrufen, gesperrt, abgelaufen oder PIN falsch (immer dieselbe Antwort) |
| `weak_password` | 400 | Passwort kürzer als die Mindestlänge (12) |
| `challenge_invalid` | 400 | Challenge unbekannt, abgelaufen oder schon benutzt |
| `invalid_code` | 400 | TOTP-Bestätigung bei der Registrierung bzw. beim nachträglichen Einrichten von Passwort + TOTP falsch |
| `registration_failed` | 400 / 409 | Registrierung mit diesen Angaben nicht möglich (z. B. E-Mail schon vergeben; keine Auskunft, warum) |
| `unauthenticated` | 401 | keine gültige Sitzung (kein/ungültiges Cookie oder Access-Token) |
| `invalid_token` | 401 | Refresh-Token ungültig, abgelaufen, widerrufen oder wiederverwendet |
| `invalid_credentials` | 401 | Anmeldung fehlgeschlagen (Konto unbekannt, Passwort/Code falsch, Konto gesperrt; ohne Unterschied) |
| `step_up_failed` | 401 | erneute Bestätigung (Step-up) falsch. **Kein Sitzungsende**: die Sitzung bleibt gültig, der Versuch zählt gegen die Sperre; Clients dürfen ihn nicht wiederholen und das Token nicht erneuern |
| `forbidden` | 403 | Rolle reicht nicht oder Objekt gehört nicht zur Familie |
| `csrf_invalid` / `origin_not_allowed` | 403 | CSRF-Header fehlt/falsch bzw. fremder `Origin` (nur Cookie-Sitzungen) |
| `step_up_required` | 403 | Bestätigung älter als 5 Minuten; dann `/auth/step-up/*`, danach wiederholen |
| `destructive_locked` | 403 | destruktive Aktion (Schlüsselwechsel `PUT /me/keys`, Passkey/Passwort/Wiederherstellungscodes ändern, Mitglied entfernen oder zurücksetzen) aus einer Sitzung, die per **Wiederherstellungscode**, **Passwort-Reset** (außer Passkey-Selbst-Reset) oder **kurz nach einer Änderung der Anmeldedaten** entstanden ist, innerhalb von 24 Stunden danach. Zusätzliche Felder `retryAfterSec` (Restdauer in Sekunden) und Header `Retry-After`; Passkey- und Passwort+TOTP-Anmeldung ohne solche Vorgeschichte sind nie gesperrt, siehe „Schlüssel-Archiv und Sperrfrist“ |
| `account_pending` | 403 | Konto wartet auf die Freigabe. Bei der Passwort- und Wiederherstellungs-Anmeldung **erst nach erfolgreicher Prüfung** von Passwort und zweitem Faktor (kein Rückschluss ohne gültige Anmeldedaten); dabei wird nichts verbraucht |
| `not_found` | 404 | Objekt unbekannt oder fremd |
| `last_admin` | 409 | der letzte Admin kann nicht herabgestuft oder entfernt werden |
| `last_credential` | 409 | der letzte Zugang einer Person kann nicht entfernt werden |
| `no_passkey` | 409 | Step-up per Passkey, aber die Person hat keinen Passkey |
| `passkey_exists` | 409 | dieser Authenticator ist schon als Passkey eingerichtet |
| `password_exists` | 409 | für das Konto gibt es schon ein Passwort (stattdessen ändern) |
| `no_password` | 409 | für das Konto ist kein Passwort eingerichtet (ändern/entfernen nicht möglich) |
| `not_pending` | 409 | freigeben/ablehnen, aber das Mitglied wartet nicht auf Freigabe |
| `cannot_remove_self` | 409 | Admin will sich selbst entfernen |
| `device_mismatch` | 409 | `/sync`: die `deviceId` im Körper passt nicht zur Sitzung (die App lädt `/me` neu und versucht es erneut) |
| `update_required` | 426 | `/sync`: `protocolVersion` kleiner als `minProtocolVersion` (`GET /version`) |
| `invite_not_open` | 409 | widerrufen/verlängern, aber die Einladung ist nicht (mehr) offen |
| `multiple_families` / `already_bootstrapped` | 409 | nur beim Einrichten per CLI (`npm run bootstrap`), nicht über die HTTP-API: mehr als eine Familie vorhanden bzw. Familie schon eingerichtet |
| `rate_limited` / `too_many_attempts` | 429 | Rate-Limit bzw. verzögerte Sperre; `Retry-After` in Sekunden |
| `server_busy` | 503 | Passwort-Berechnung ausgelastet (es wird kein Fehlversuch gezählt) bzw. beim Sync: die Familie ist gerade gesperrt oder die Anweisung lief zu lange (`Retry-After`, nichts wurde geändert) |
| `internal_error` | 500 | unerwarteter Fehler |

**Sitzungsende aus Sicht der App:** Nur `401 unauthenticated` und `401 invalid_token` bedeuten, dass die Sitzung ungültig ist (die App erneuert dann einmal bzw. meldet ab). Alle anderen 401-Fachcodes (`step_up_failed`, `invalid_credentials`) beenden die Sitzung nicht und werden nicht wiederholt.

Antworten der API tragen `Cache-Control: no-store`.

**Anmeldearten und Sitzungen**

- **Web (Cookie):** Nach der Anmeldung setzt der Server `__Host-lxsid=<Token>; Path=/; Secure; HttpOnly; SameSite=Strict` (kein `Domain`). Die Antwort enthält
  `session.csrfToken`; **jede ändernde Anfrage (POST, PUT, PATCH, DELETE)** mit Cookie muss es im Header `X-CSRF-Token` mitsenden (sonst `403 csrf_invalid`).
  Zusätzlich wird ein fremder `Origin`-Header bei ändernden Anfragen abgelehnt (`403 origin_not_allowed`). `GET /me` liefert das Token erneut (nach einem Neuladen).
  Cookie-Sitzung: 30 Tage absolut, 7 Tage Leerlauf.
- **App (Token):** Anmeldung mit `client: "app"` und `device`. Antwort: `accessToken` (15 min, `Authorization: Bearer <accessToken>`, kein CSRF-Header nötig),
  `refreshToken` (einmal einlösbar, 90 Tage absolut, 30 Tage Leerlauf) und `deviceId`. `POST /auth/refresh` tauscht das Refresh-Token gegen ein neues Paar (Rotation).
  Wird ein bereits eingelöstes Refresh-Token erneut vorgelegt (auch gleichzeitig), widerruft der Server die **ganze Token-Familie** und schreibt `session_reuse_detected` ins Audit-Log.
  **Ausnahme: Wiederholung im Toleranzfenster** (verlorene Antwort), siehe unten.
  Ein vorhandener, aber ungültiger `Authorization`-Header fällt nie auf das Cookie zurück.
- **Step-up:** Die Anmeldung zählt als frische Bestätigung. Wiederverwendbare Prüfung (`requireStepUp`, 5 Minuten): Rollenänderung, Mitglied entfernen/zurücksetzen,
  Admin-Einladung erzeugen, neuen Passkey hinzufügen/entfernen, Wiederherstellungs-Codes neu erzeugen (später: Tresor, Familie löschen). Ist die Bestätigung älter,
  antwortet der Server mit `403 step_up_required`; die Bestätigung erfolgt über `/auth/step-up/*`.

**Wiederholung des Refresh-Tokens (Toleranzfenster).** Geht die Antwort auf `POST /auth/refresh` unterwegs verloren (Funkloch nach dem Senden), kennt die App das neue Paar nicht, das alte Token ist aber schon eingelöst. Damit daraus kein Widerruf der Familie wird, bedient der Server eine Wiederholung, wenn **alle** Bedingungen gelten:

1. höchstens **30 Sekunden** seit dem Einlösen (festes Fenster ab dem ersten Einlösen, kein gleitendes; Konstante `refreshGraceSec` in `server/src/config.ts`),
2. **dieselbe `deviceId`** wie beim Einlösen (sie liegt nur auf dem Gerät),
3. die **Nachfolgerin ist noch unbenutzt** (nicht eingelöst, nicht widerrufen).

Dann widerruft der Server die erste, nie angekommene Nachfolgerin und stellt **genau ein** neues Paar aus (immer nur ein lebender Nachfolger je Familie; Audit-Ereignis `session_refresh_retry`). Mehrfache und gleichzeitige Wiederholungen im Fenster sind erlaubt und werden nacheinander bedient (Zeilensperre); es bleibt bei einem lebenden Nachfolger. Alles andere bleibt **echte Wiederverwendung** und widerruft die ganze Familie: Wiederholung nach mehr als 30 Sekunden, von einer anderen `deviceId`, oder nachdem die Nachfolgerin schon benutzt wurde. Das Fenster ersetzt kein Wiederholen auf Verdacht: Die App sendet ein Refresh-Token nur dann erneut, wenn sicher ist, dass die Anfrage den Server nie erreichte (Fehler beim Verbindungsaufbau); bei unklarem Ausgang meldet sie ab. Sicherheitsbetrachtung: PROJEKTBESCHREIBUNG.md, Abschnitt 7.

**Rate-Limits:** 300 Anfragen/min je IP insgesamt; `/auth/*`, `/ws-ticket`, `/invites` (POST), `/members/:id/reset`, `PUT /me/family-role`, `PUT /members/:id/family-role`, `/me/passkeys/*` und `/me/key-backups/archive*` strenger (10/min); `POST /sync` 120/min je IP (`SYNC_RATE_LIMIT_MAX`) und zusätzlich je Gerät und Person (Abschnitt „Sync“, Limits). Zusätzlich zählt der Server
Fehlversuche (Passwort, TOTP, Wiederherstellungs-Code, Step-up) je **IP**, je **Konto** und je **Paar aus Konto und IP** und sperrt verzögert: Konto+IP ab 5, IP ab 20, Konto ab 10 Fehlversuchen
30 s, danach doppelt so lang, **höchstens 90 s** (so lässt sich ein fremdes Konto nicht lange aussperren; die tippende IP ist früher dran als das Konto). Anmeldung und Step-up teilen sich denselben Konto-Schlüssel.
**Passkey-Anmeldungen hängen nicht an der Konto-Sperre** (nur IP-Sperre). IPv6-Adressen gelten als **/64-Präfix** (IP-Sperre, Rate-Limit, Verbindungslimit am WebSocket); IPv4-in-IPv6 als IPv4.
WebSocket-Anmeldefehler zählen mit. Die Erzeugung von Challenges ohne Anmeldung (`/auth/login/passkey/options`, Start der Registrierung) ist je IP-Präfix (20) und insgesamt (2000 offene) begrenzt, sonst `429 rate_limited`.

**Eingaben:** Zeichenketten mit NUL (`\u0000`) oder einzelnen Surrogaten (`\ud800`) werden überall (auch verschachtelt und in Schlüsseln) mit `400 invalid_request` abgelehnt.
**Überlast:** Sind alle Passwort-Berechnungen (Argon2id, 2 gleichzeitig) und die Warteschlange (16) belegt, antwortet der Server `503 server_busy` mit `Retry-After` (kein Fehlversuch wird gezählt).

**Rollen:** `admin`, `parent`, `child`. Die frühere Rolle `guest` (Gast) gibt es seit Migration 0005 nicht mehr; Zugriff haben nur eingeladene Familienmitglieder. Eine Einladung mit `role: "guest"` ergibt `400 invalid_request`. Alle Zugriffe sind auf die eigene Familie begrenzt; Objekte einer fremden Familie liefern `404`.

## Einladung einlösen (ohne Anmeldung)

Das Token steht im Einladungslink im **URL-Fragment** (`https://familie.lx-labs.dev/#/einladung/<token>`) und wird von der App nur im **POST-Body** gesendet.

| Methode, Pfad | Body | Antwort |
| --- | --- | --- |
| `POST /auth/invites/lookup` | `{ token }` | `{ invite: { role, pinRequired, requireApproval, familyName, reset, kind (standard \| password_reset), displayName?, email?, expiresAt } }` (`email` nur bei Reset-Einladungen und mit Schalter `E2EE_PW_BACKUP`); jeder ungültige Fall (unbekannt, benutzt, widerrufen, gesperrt, abgelaufen) ergibt dieselbe `400 invite_invalid` |
| `POST /auth/invites/passkey/options` | `{ token, pin?, email?, displayName? }` | `{ challengeId, options }` (WebAuthn-Registrierungsoptionen, Challenge serverseitig, 5 min) |
| `POST /auth/invites/passkey/complete` | `{ challengeId, response, client?, device?, label? }` | `{ member, status, recoveryCodes[10], session? }` |
| `POST /auth/invites/password/start` | `{ token, pin?, email?, displayName?, password }` | `{ challengeId, totpSecret, totpUri }` (noch kein Konto; Passwort mindestens 12 Zeichen) |
| `POST /auth/invites/password/complete` | `{ challengeId, code, client?, device? }` | wie oben; `code` = 6-stelliger TOTP-Code aus der Authenticator-App |

- Bei Einladungen zum **Zurücksetzen** (`reset: true`) entfallen `email` und `displayName`.
- `status: "pending"`: Das Konto wartet auf die Freigabe durch einen Admin; es gibt keine Sitzung und die Anmeldung antwortet `403 account_pending`.
- `recoveryCodes` (10 Stück, Format `XXXX-XXXX-XXXX-XXXX`) erscheinen **nur hier** im Klartext.
- **PIN:** Jeder Versuch wird vor dem Vergleich gezählt; nach 5 Fehlversuchen ist die Einladung gesperrt (auch mit richtiger PIN). Antwort immer `400 invite_invalid`.
- `client`: `"web"` (Standard, setzt das Cookie) oder `"app"` (Tokens im Body). `device`: `{ id?, name, platform: android|ios|web|windows|linux|macos, appVersion? }`.

## Anmeldung (ohne Anmeldung)

| Methode, Pfad | Body | Antwort |
| --- | --- | --- |
| `POST /auth/login/passkey/options` | `{}` | `{ challengeId, options }` (ohne Kontoangabe: auffindbare Passkeys, `userVerification: required`) |
| `POST /auth/login/passkey/verify` | `{ challengeId, response, client?, device? }` | `{ user, session }`; geprüft werden Challenge, Origin, RP-ID, Nutzerprüfung, Signatur und `signCount` (Rückgang = abgelehnt und `passkey_counter_regression` im Audit-Log) |
| `POST /auth/login/password` | `{ email, password \| authKey, upgradeAuthKey?, totp \| recoveryCode, client?, device? }` (Klartext `password` oder abgeleiteter `authKey`, siehe „Anmeldung mit `authKey`“; `upgradeAuthKey` nur mit `password`) | `{ user, session }`; **Passwort nur mit zweitem Faktor**; ein TOTP-Zeitschritt gilt nur einmal (Replay-Schutz). Der zweite Faktor wird erst nach der Statusprüfung (aktiv, nicht gesperrt) und gemeinsam mit der Sitzungserstellung in einer Transaktion verbraucht: bei `account_pending` und bei gesperrten Konten bleibt Code bzw. Zeitschritt unverändert |
| `POST /auth/login/recovery` | `{ email, code, client?, device? }` | `{ user, session, recoveryCodesRemaining }`; Einmal-Code, Sitzung gilt als frisch bestätigt; verbraucht wird der Code nur bei aktivem Konto (pending: `403 account_pending` nach gültigem Code, nichts verbraucht; gesperrt: `401 invalid_credentials`) |
| `POST /auth/refresh` | `{ refreshToken, deviceId }` | `{ session }` (neues Token-Paar); Gerät muss zum Token passen |

`session` (Web): `{ kind: "web", csrfToken, expiresAt, deviceId }` + Cookie. `session` (App): `{ kind: "app", accessToken, accessExpiresAt, refreshToken, refreshExpiresAt, deviceId }`.

### Schlüssel-Archiv und Sperrfrist (P0-2 „Kein Datenverlust“)

**Nichts geht verloren.** Ein Schlüsselwechsel verschiebt die Wiederherstellungssicherung (`key_backups`) in das Archiv (`key_backup_archive`, `reason: rotation`); ersetzt eine neue Sicherung zur selben Version die bisherige durch einen **anderen** Blob, landet die bisherige dort mit `reason: replaced` (so zerstört auch eine Müll-Sicherung eines Angreifers mit geliehener Sitzung nichts; Sicherheitsereignis `key_backup_replaced`). Die Passwort-Sicherungen (`key_backups_pw`) bleiben in ihrer Tabelle: die aktuelle wird beim Wechsel `stale`, ersetzte `superseded`; das Archiv bietet sie mit an (**superseded oder stale** zu einem **älteren Schlüsselstand**, sowie **bestätigte** ersetzte Zeilen desselben Stands; nie `pending`, nie die aktuelle). Eine ältere Schlüsselversion überschreibt den aktuellen Zugang nie (`PUT /me/key-backup[-pw]` mit älterer Version `409 key_version_mismatch`).

**Umfang und Ausdünnen.** Einträge früherer Schlüsselstände (`reason: rotation`, bei Passwort-Sicherungen nur bestätigte) kommen **immer vollständig und zuerst** und werden **nie** gelöscht oder ausgedünnt. Nur ersetzte Sicherungen desselben Stands (`reason: replaced`) werden begrenzt: die Liste zeigt die neuesten 50; in `key_backup_archive` behält der Server je Schlüsselstand die **ältesten 5** (dort liegt die echte Sicherung, auch nach einer Flut von Müll-Ersetzungen) und insgesamt die neuesten 50 (ältere `replaced`-Zeilen werden beim Ersetzen gelöscht); bei Passwort-Sicherungen wird nichts gelöscht, nur die Liste begrenzt. **Ohne Schalter `E2EE_PW_BACKUP`** gibt es nur Wiederherstellungssicherungen (Liste, Zahl `archiveCount` und Einzelabruf sind dann gleich konsistent; Passwort-Zeilen kommen mit dem Schalter wieder).

| Methode, Pfad | Rolle | Beschreibung |
| --- | --- | --- |
| `GET /me/key-backups/archive` | alle, Step-up | `?limit=1..200` (Standard 100), `?before=<next>` → `{ entries: [{ id, kind, keyVersion, createdAt, archivedAt, reason, verified }], next }`, **nie ein Blob**. Reihenfolge fest: erst alle `rotation`, dann die neuesten `replaced`, je neueste zuerst; `next` (opak, `null` am Ende) ruft die Folgeseite ab, andere Parameter und ungültige Werte `400`. `kind`: `recovery` oder `password`; `verified`: eine Passwort-Sicherung war einmal per Round-Trip bestätigt (Wiederherstellungssicherungen immer `true`). Audit `key_backup_archive_list` |
| `GET /me/key-backups/archive/:id` | alle, Step-up | wie ein Eintrag, dazu `blob` und bei `kind: password` `kdf: { id, memKiB, ops, salt }` (zum Ableiten des alten Schlüssels mit dem damaligen Passwort; die App nutzt es als „Archivschlüssel“ zum Öffnen alten Verlaufs). Nur die **eigene** Person: fremde, unbekannte, `pending`- und nicht archivierte IDs `404`, ungültige `400`. Abruf, Audit `key_backup_archive_read` und Sicherheitsereignis in einer Transaktion. **Nicht** durch die Sperrfrist gesperrt (wer sich mit einem Code anmeldet, braucht genau diesen Weg) |

Beide Routen: strenges Rate-Limit (10/min). Der Server kann die Blobs nicht lesen; Blob und Salt erscheinen nie im Log oder Audit. **Bewusste Abwägung:** Passwort-Sicherungen (auch `stale`) und das Archiv bleiben mit Step-up abrufbar, auch aus einer Code-Sitzung: wer nur einen Code hat, bekommt Blobs, die er ohne Passwort bzw. Wiederherstellungsschlüssel nicht öffnen kann (offline raten gegen Argon2id bleibt das Restrisiko eines schwachen Passworts); sie zu sperren würde genau den Rettungsweg verbauen.

**Sperrfrist.** Jede Sitzung merkt ihre Herkunft (`sessions.origin`, Zeitpunkt `origin_at`): `login` (Passkey, Passwort + TOTP), `recovery_code` (Anmeldung mit einem Wiederherstellungscode, auch `POST /auth/login/password` mit `recoveryCode` statt TOTP), `password_reset` (Sitzung nach „Passwort vergessen?“ mit **Wiederherstellungscode** und nach dem Admin-Link) oder `access_change` (jede Anmeldung, die **innerhalb von 24 Stunden nach einer Änderung der Anmeldedaten** durch die Person selbst entsteht: Passkey hinzufügen/entfernen, Passwort setzen/ändern/entfernen, Wiederherstellungscodes neu erzeugen; `origin_at` = diese Änderung, `users.access_changed_at`; Registrierung und Passwort-Reset setzen es nicht). Eine Refresh-Rotation übernimmt Herkunft und Zeitpunkt unverändert. Der **Passkey-Selbst-Reset** („Passwort vergessen?“ mit Passkey) ist dagegen eine normale Anmeldung (`login`): der Passkey hat die Person ausgewiesen. Aus Sitzungen mit Herkunft `recovery_code`, `password_reset` oder `access_change` sind **24 Stunden** lang gesperrt (`403 destructive_locked` mit `retryAfterSec` und `Retry-After`, Prüfung vor dem Step-up): Schlüsselwechsel (`PUT /me/keys`), Passkey hinzufügen/entfernen (`/me/passkeys/*`), Passwort setzen/ändern/entfernen (`/me/password/*`), `POST /me/recovery-codes`, `DELETE /members/:id` und `POST /members/:id/reset` (eine Admin-Sitzung aus einer solchen Herkunft; normale Admin-Sitzungen und das CLI bleiben frei). So kann ein Angreifer mit einem erbeuteten Code weder sofort alle Wiederherstellungswege entwerten noch sich einen neuen „normalen“ Zugang anlegen (die Anmeldung damit erbt die Frist). **Nie gesperrt:** das normale Anlegen und Bestätigen einer Sicherung (`PUT`, `verified`; Ersetztes wird archiviert), alle Lese-Routen und das Archiv. Nicht gesperrt bleibt die Sitzung nach einem Komplett-Reset-Link (Einladung, Herkunft `login`).

**Benachrichtigung.** Schlüsselwechsel, Ersetzen und Abruf der Wiederherstellungs-, Passwort- und archivierten Sicherung (nicht der Round-Trip-Abruf einer eigenen `pending`-Sicherung), Anmeldung per Wiederherstellungscode und die Geräte-Übertragung erzeugen ein Sicherheitsereignis (`GET /me/security-events`, feste Codes siehe dort) und einen Push-Wecker **ohne Inhalt** (derselbe feste Wecker wie beim Passwort-Reset). Der Wecker geht an die aktiven Geräte der Person **ohne das auslösende Gerät**. **Entprellung:** Lese-Ereignisse und Übertragung je Art und Person höchstens einmal in 10 Minuten, Wecker dazu höchstens einer je Person in 60 Sekunden; die kritischen Arten (`key_rotated`, `key_backup_replaced`, `recovery_code_login`, Resets, `member_account_reset`) werden nie entprellt. Das Einlösen einer Übertragung erzeugt nur das Ereignis.

**Komplett-Reset (`POST /members/:id/reset`, auch `bootstrap --reset`):** zusätzlich zum Ereignis `account_reset_requested` für die Person bekommen **alle anderen aktiven Mitglieder** der Familie das Ereignis `member_account_reset` (`subjectName` = die zurückgesetzte Person) und den Wecker; Text der App: „Zugang von <Name> wurde zurückgesetzt; nimm einen neuen Schlüssel dieser Person nur nach Rücksprache an.“ Wartende und gesperrte Konten bekommen nichts. Der Hinweis ist Nebensache: Ereignisse werden in einem eigenen Teilabschnitt der Transaktion gespeichert, Themenabfragen und Wecker laufen nach dem Commit gebündelt; ein Fehler dort wird nur geloggt und lässt weder den Reset noch den Einladungslink scheitern.

**Mitglied entfernen: Soft-Delete (P1, Migration 0022).** `DELETE /members/:id` löscht nichts Endgültiges mehr (Sperrfrist wie bisher). Die Person bekommt `users.disabled_at`, `users.removed_at` (Prüfung `users_removed_ck`: entfernt heißt immer auch gesperrt) und `removed_by`; ihre Sitzungen, Geräte und Push-Endpunkte enden. **Es bleiben liegen:** Konto und Anmeldedaten, Personenschlüssel samt Historie, Wiederherstellungs- und Passwort-Sicherungen, **Archiv**, Übertragungen und Sicherheitsereignisse. **Es wird wie bisher gelöst** (nicht wiederherstellbar): Verweise in Listen, Aufgaben und Terminen, Teilnahmen an Chats (Direktchats der Person enden, Gruppen verlieren sie), Termin-Teilnahmen. Die Person kann sich nicht anmelden (gleiche Antwort wie bei einem falschen Passwort), steht in keiner Mitgliederliste, zählt nicht mehr als Admin (der letzte wirksame Admin bleibt geschützt), ist im Sync kein gültiger Verweis mehr (`invalid_reference`) und fehlt in Ampel und Zählern. **Frist:** `REMOVED_RETENTION_DAYS` = 30 Tage; der stündliche Aufräum-Job (`runMaintenance`, Bericht `removedMembersPurged`) löscht danach endgültig mit allem, was daran hängt (Kaskade wie früher beim sofortigen Entfernen; Audit `member_purged`); eine Wiederherstellung zwischen Auswahl und Löschen erkennt er unter Zeilensperre. In der Zeit holt `POST /members/:id/restore` die Person zurück. Die Chat-Teilnahmen kehren nicht von selbst zurück: Familie und Gruppen nehmen die Person wie jede neue Person nach Rückfrage auf (Aufnahme-Abfrage der App). **Die E-Mail-Adresse bleibt in der Zeit belegt** (eindeutig je Konto): soll dieselbe Adresse neu eingeladen werden, zuerst zurückholen, vorzeitig endgültig löschen (`POST /members/:id/purge`) oder bis Tag 30 warten; der Hinweis steht im Entfernen-Dialog und im Bereich „Kürzlich entfernt“ der App; beim Einladen kommt er nur über die API als Admin (`POST /invites` mit `email`, `409 member_removed`), die App sendet keine Adresse. Wer sich mit der blockierten Adresse registriert, bekommt nur die allgemeine Meldung. Entfernte Konten werden von `PUT /members/:id/family-role`, dem Komplett-Reset (`POST /members/:id/reset`, auch das CLI `bootstrap --reset`, dort mit klarer Meldung) und dem Passwort-Reset abgelehnt. **Betreiber: vor dem endgültigen Löschen (Tag 30) ist bei Bedarf ein Snapshot der Datenbank sinnvoll** (`deploy/backup/lx-fampad-backup.sh`).


### Passwort-Sicherung des Schlüssels (vereinfachte Schlüsselverwaltung, Schalter `E2EE_PW_BACKUP`)

**Nur mit `E2EE_PW_BACKUP=true` (Standard aus):** Ohne den Schalter gibt es diese Routen nicht, sie antworten wie jede unbekannte Route mit `404 not_found`; `GET /version` meldet den Stand als `features: { pwBackup, authKey, legacyPasswordLogin, wrapKeyVersion }` (Booleans; `authKey` = `pwBackup`; `wrapKeyVersion` folgt dem Schalter `E2EE_WRAP_KEY_VERSION` (Standard aus) und sagt, ob der Server Wraps mit Schlüsselversion annimmt, siehe „Epochen und Schlüssel-Wraps“)
(alte Apps ignorieren das Feld). Die Sicherung ist **zusätzlich** zum Wiederherstellungsschlüssel und zur Geräte-Übertragung (Abschnitt davor, unverändert). Der Server sieht nie Passwort, `authKey` oder `kek`: Der Blob ist mit dem auf dem Gerät
abgeleiteten Schlüssel verschlüsselt und für ihn undurchsichtiger Base64url-Text. Blob und Salt erscheinen nie im Log oder Audit. Alles strikt geprüft (unbekannte Felder `400`), strenges Rate-Limit wie die Anmeldung (Standard 10 je Minute und IP).

**Ableitungssatz `kdf` = `{ id, memKiB, ops, salt }`:** Es gibt ein festes Profil für alle Konten: `id: "argon2id-v1"`, `memKiB: 65536`, `ops: 3` (Wechsel nur global per Code, nie je Konto, sonst wäre das Profil ein Konto-Orakel). Der **Salt** (16 Byte, Base64url) wird **immer vom Server bestimmt**:
HMAC über `AUTH_SECRET_KEY` aus der normalisierten E-Mail und der Salt-Generation (Standard 1, für jedes Konto). Der Client liefert nie einen Salt und keine freien Zahlen. Eine Salt-Rotation (höhere Generation) wäre eine eigene, seltene, protokollierte Aktion und ist nicht Teil dieses Pakets.
Jede Sicherungszeile speichert ihren eigenen Satz (`kdf_id`, `mem_kib`, `ops`, `salt_generation`), ältere (ersetzte) Zeilen bleiben so lesbar.

| Methode, Pfad | Rolle | Beschreibung |
| --- | --- | --- |
| `POST /auth/kdf-params` | ohne Anmeldung | `{ email }` → `{ kdf }`: Satz **vor** der Anmeldung. Für **jede** E-Mail (bekannt, unbekannt, deaktiviert, mit oder ohne Sicherung) dasselbe Profil und ein aus E-Mail und Generation abgeleiteter Salt, immer genau eine Abfrage: kein Orakel für die Existenz eines Kontos und kein Wechsel der Antwort beim ersten Ablegen |
| `PUT /me/key-backup-pw` | alle, Step-up | `{ blob (96 bis 4096 Zeichen), keyVersion, kdf: { id, memKiB, ops } }` (kein Salt) → `{ ok, id }`: `kdf` muss genau dem festen Profil entsprechen (sonst `409 kdf_mismatch`). Legt eine neue Sicherung als **`pending`** (unbestätigt) an; die bisherige aktuelle (`active`/`stale`) bleibt **unberührt und gültig**, bis die neue bestätigt ist. Eine eigene ältere `pending`-Zeile wird `superseded` (alles in **einer** Transaktion mit dem Audit `key_backup_pw_set`; gleichzeitige Aufrufe laufen nacheinander; höchstens eine `pending` je Person per Teil-Unique-Index). Eine `pending`-Zeile, die nicht binnen einer Stunde bestätigt wird, setzt der Aufräumjob auf `superseded` (nie gelöscht); ein Schlüsselwechsel tut das sofort. `keyVersion` muss zur aktuellen Schlüsselversion passen (`409 key_version_mismatch`), ohne Schlüssel `409 no_keys`. Alte Zeilen werden **nie gelöscht**. Die Datenbank erzwingt zusätzlich Profil (`argon2id-v1`, mindestens 65536 KiB und 3 Durchgänge) und Blob-Länge |
| `GET /me/key-backup-pw` | alle, Step-up | `{ id, blob, keyVersion, state, kdf }` der aktuellen, **bestätigten** Sicherung; mit `?pending=1` stattdessen die eigene, noch unbestätigte (`state: pending`, für den Round-Trip der App; nur der Besitzer, andere Parameter `400`) (`state`: `active`, oder `stale`, wenn der Personenschlüssel seither gewechselt hat: sie enthält dann den **alten** Schlüssel und darf nie als Wiederherstellung des aktuellen gelten); `404` ohne Sicherung. Abruf und Audit `key_backup_pw_read` in einer Transaktion; der Abruf der **aktuellen** Sicherung erzeugt zusätzlich ein Sicherheitsereignis `key_backup_pw_read` entprellt (höchstens eines je 10 Minuten), samt Wecker auf die anderen Geräte (der Round-Trip-Abruf `?pending=1` nicht) |
| `POST /me/key-backup-pw/verified` | alle, Step-up | `{ id }` bestätigt die eigene `pending`-Sicherung (erst nach der Round-Trip-Probe der App): in **einer** Transaktion wird die bisherige aktuelle (`active`/`stale`) `superseded` und die `pending`-Zeile `active` mit `verified_at` (Sperre auf `person_keys`; die Schlüsselversion muss noch passen). Fremde oder unbekannte `id` `404`, ersetzte, verfallene oder zu einer älteren Schlüsselversion gehörende `409 backup_not_current`; eine schon bestätigte aktuelle `id` bestätigt erneut folgenlos (`200`). Audit `key_backup_pw_verified` |

### Anmeldung und Passwortwechsel mit `authKey` (PR 4, Schalter `E2EE_PW_BACKUP`, Stichtag `AUTH_LEGACY_PASSWORD_LOGIN`)

Die App leitet aus E-Mail und Passwort per Argon2id (Salt und Profil: `POST /auth/kdf-params`) einen Master ab und daraus per BLAKE2b zwei unabhängige Teilschlüssel: `authKey` (geht an den Server **statt des Passworts**) und `kek` (bleibt auf dem Gerät, verpackt den Personenschlüssel). Der Server speichert nie den `authKey`, sondern nur `HMAC-SHA256(Schlüssel aus AUTH_SECRET_KEY, userId|authKey)` in `password_authkeys` (je Passwort-Eintrag eine Zeile, an die Person gebunden, Vergleich in konstanter Zeit).

- **Format `authKey`:** 32 Byte als Base64url ohne Auffüllung, genau 43 Zeichen, kanonisch (nur die eine Schreibweise je Wert); sonst `400 invalid_request`.
- **Fähigkeit:** `GET /version` meldet `features.authKey` (= `E2EE_PW_BACKUP`; ohne Schalter wird `authKey` in jedem Body mit `400` abgelehnt) und `features.legacyPasswordLogin` (= `AUTH_LEGACY_PASSWORD_LOGIN`, Standard `true`). Fehlt `features.authKey` (älterer Server), sendet die App das Klartext-Passwort wie bisher.
- **Zustand je Konto** (nur abgeleitet): `legacy` (Passwort-Eintrag ohne Zeile in `password_authkeys`: nur Klartext-Anmeldung), `authkey` (mit Zeile), `none` (kein Passwort, nur Passkey). Es gibt keinen Weg zurück außer Passwort entfernen und per Klartext (alte App) neu einrichten.
- **Eingabe überall „Klartext ODER authKey“:** `POST /auth/login/password` und `POST /auth/invites/password/start` (`{ …, password | authKey }`), `POST /me/password/start` und `POST /me/password/change` (`{ password | authKey }`). Genau eins von beiden, sonst `400`. Mit `authKey` prüft der Server die Passwortstärke **nicht** (er kennt das Passwort nie): Länge und Regeln gelten allein in der App.
- **Anmeldung:** `{ email, authKey, totp | recoveryCode, client?, device? }` → wie bisher `{ user, session }`. Dieselben Schritte, Sperren (IP, Konto, Paar) und dieselbe Antwort `401 invalid_credentials` für unbekanntes, deaktiviertes, `legacy`- und falsches Konto; unbekannte Konten rechnen gegen einen Platzhalter-Prüfwert (kein Zeit- oder Antwort-Orakel). Der zweite Faktor wird weiter erst nach dem Passwort-Teil und gemeinsam mit der Sitzung verbraucht.
- **Umstellung `legacy` → `authkey` beim Anmelden:** `{ email, password, upgradeAuthKey, totp | recoveryCode }` (nur mit `password`, nur mit Schalter): Nach erfolgreicher Prüfung von Passwort **und** zweitem Faktor legt der Server den Prüfwert in **derselben Transaktion** wie die Sitzung an bzw. ersetzt ihn (Audit `password_authkey_set`); scheitert etwas, bleibt das Konto `legacy`. Der alte Klartext-Hash bleibt (alte Apps), solange `AUTH_LEGACY_PASSWORD_LOGIN=true` ist.
- **Passwortwechsel mit `authKey`:** `POST /me/password/change` `{ authKey, pwBackupId? }` ersetzt das Passwort (der Klartext-Hash ist danach ein Platzhalter `!authkey`: Klartext-Anmeldung dieses Kontos ist nicht mehr möglich). Mit `pwBackupId` (nur mit `authKey`) wird die vorher abgelegte, von der App per Round-Trip geprüfte Passwort-Sicherung in **derselben Transaktion** die aktuelle (die bisherige wird `superseded`): neues Passwort und Sicherung gelten gemeinsam oder gar nicht; ungültige Kennung ergibt `404`/`409` und **nichts** ändert sich. Ohne `pwBackupId` bleibt eine vorhandene Sicherung unberührt und gehört weiter zum alten Passwort (die App weist darauf hin).
- **Klartext-Wechsel gesperrt:** Ein Konto im Zustand `authkey` oder mit Passwort-Sicherung ändert sein Passwort nicht mehr per Klartext (`409 password_change_needs_update`): eine alte App könnte weder die Sicherung nachziehen noch den `authKey` setzen.
- **Stichtag `AUTH_LEGACY_PASSWORD_LOGIN=false`:** Jede Anfrage mit Klartext-`password` (Anmeldung, Registrierung, Einrichten, Ändern) wird **vor jeder Konto-Abfrage** mit `403 legacy_login_disabled` abgewiesen (für jede E-Mail gleich, kein Fehlversuch). Der Start bricht ab, wenn der Schalter `false` ist, aber `E2EE_PW_BACKUP` nicht `true` (sonst könnte sich niemand mehr mit Passwort anmelden); unbekannte Werte brechen den Start ab.
- **Admin-Übersicht (nur lesend, nur Admins, nur mit Schalter):** `GET /members/password-modes` → `{ legacyPasswordLogin, modes: [{ userId, mode: "legacy" | "authkey" | "none" }] }` (nie ein Prüfwert). Die App zeigt in der Mitglieder-Ansicht eine kleine Markierung bei `legacy`, damit der Stichtag erst gesetzt wird, wenn alle umgestellt sind. `GET /members` bleibt unverändert.
- **Einladung zum Zurücksetzen:** `POST /auth/invites/lookup` liefert bei einer Reset-Einladung (und nur mit Schalter) zusätzlich `email` des Kontos: die App braucht sie für den Salt der Passwort-Ableitung.
- **Fehlercodes neu:** `403 legacy_login_disabled`, `409 password_change_needs_update`.

**Warnung Rückschalten:** Wird `E2EE_PW_BACKUP` ausgeschaltet, `AUTH_LEGACY_PASSWORD_LOGIN` auf `false` gesetzt oder der Server auf einen Stand vor PR 4 zurückgestellt, können sich Konten mit authKey-Passwort (Platzhalter im Klartext-Hash) nicht mehr per Passwort anmelden, nur noch per Passkey oder Wiederherstellungscode; Der Passwort-Reset (PR 4b, Abschnitt „Passwort zurücksetzen“) ist der Rückweg. Die App sendet für solche Konten nie Klartext. Reihenfolge beim Ausrollen: **erst den Server, dann die Web-App und die APK**.

**Rollout-Hinweis (wichtig):** Setzt ein Mitglied sein Passwort mit `authKey` neu (Passwort ändern, einrichten) oder wird ein Konto per Reset-Einladung neu eingerichtet, ist der Klartext-Hash ein Platzhalter: **alle noch nicht aktualisierten Geräte (App 0.5.x/0.6.0) dieses Mitglieds können sich dann auch vor dem Stichtag nicht mehr mit Passwort anmelden.** Reihenfolge deshalb: erst auf allen Geräten die neue App, dann das Passwort ändern. Den Stichtag (`AUTH_LEGACY_PASSWORD_LOGIN=false`) erst setzen, wenn `GET /members/password-modes` keinen `legacy`-Eintrag mehr zeigt (oder nach PR 4b mit Admin-Passwort-Reset als Rückweg).

**Zweiter Faktor:** Richtiger `authKey` mit falschem oder fehlendem zweiten Faktor antwortet bewusst genauso `401 invalid_credentials` wie ein falscher `authKey` (gleiche Zähler, gleicher Aufwand): ein eigener Fehler wäre ein Passwort-Orakel am zweiten Faktor vorbei. Folge: Die App wiederholt nach `invalid_credentials` auf einem Gerät, das das Konto per authKey kennt (Vermerk), nie mit Klartext; auf einem **neuen** Gerät bleibt die Wiederholung mit Klartext bis zum Stichtag möglich, ein Tippfehler im Code sendet das Passwort also einmal an den eigenen Server (so war es vor diesem PR immer). Ein falsches Passwort auf einem unbekannten Gerät zählt zwei Fehlversuche (authKey-Versuch und Klartext-Wiederholung). Ein 404 von `GET /version` gilt nur bei JSON-Antwort des Servers als „älterer Server“, eine HTML-Seite eines Proxys wie ein Ausfall.

**Hinweis Stärkeprüfung:** Mit `authKey` kann der Server die Passwortstärke nicht prüfen; Länge, Zufallswörter-Vorschlag und Kontodaten-Regeln gelten nur in der App (ein manipulierter Client könnte ein schwaches Passwort setzen; das trifft nur dessen eigenes Konto). **Ausfall von `GET /version`:** Netzfehler, Zeitüberschreitung, 429 und 5xx werden nie als „kein authKey“ gewertet; die App zeigt „keine Verbindung“ und sendet nichts (zuletzt bekannte Fähigkeiten merkt sie im `TokenStore`). Der Vermerk „Konto per authKey angemeldet“ liegt auf Android im Keystore-Speicher, im Web im `localStorage` (nur E-Mail in Kleinschreibung, kein Geheimnis) und bleibt beim Abmelden. `promotePwBackup` mit `pwBackupId` gilt nur für eine **unbestätigte** (`pending`) Zeile (`409 backup_not_current` bei einer aktiven); `POST /me/password/start` mit Klartext bei vorhandener Passwort-Sicherung `409 password_change_needs_update`.

**Pflichten der App** (`passwort_anmeldung.dart`): (1) Nur ein authKey verlässt das Gerät, solange der Server `features.authKey` meldet. (2) Wiederholung mit Klartext + `upgradeAuthKey` **nur** nach `401 invalid_credentials` des authKey-Versuchs, **nur** solange `features.legacyPasswordLogin` und **nur**, wenn diese App das Konto nie per authKey angemeldet hat (Vermerk im `TokenStore`, bleibt beim Abmelden); 429, `account_pending`, Netzfehler und alles andere gehen unverändert nach oben. (3) Ist die Ableitung auf dem Gerät nicht möglich (Bibliothek, unbekanntes Verfahren), gilt dasselbe: Klartext nur solange erlaubt und das Konto nicht gemerkt ist, sonst Fehlermeldung. (4) Der Passwortwechsel legt zuerst die neue Sicherung ab und prüft sie (Probe + Round-Trip), erst dann `password/change` mit `pwBackupId`; scheitert die Prüfung, ändert sich nichts.

Ein Schlüsselwechsel (`PUT /me/keys`) löscht die Passwort-Sicherung **nicht**, sondern setzt die aktuelle auf `stale` (die Schlüsselversion zählt hoch) und eine unbestätigte auf `superseded`; die alte Wiederherstellungssicherung (`key_backups`) wandert ins Archiv (`key_backup_archive`). Alles Ersetzte bleibt über `GET /me/key-backups/archive` erreichbar.

**Pflichten des Clients (für die App):** (1) Beim Verschlüsseln den Satz (`id`, `memKiB`, `ops`, Salt) und `userId`, `keyVersion` als **AAD** binden. (2) Nach dem Entschlüsseln den öffentlichen Schlüssel gegen `person_keys` (Server) **und** den TOFU-Speicher prüfen, bei Abweichung nichts übernehmen. (3) Eine **feste Untergrenze** im Client (Profil `argon2id-v1`, 65536 KiB, 3 Durchgänge), nie Parameter aus der Serverantwort herabsetzen (Downgrade-Schutz). (4) `stale` nie zur Wiederherstellung benutzen und `verified` nur nach erfolgreicher Round-Trip-Probe senden.

### Passwort zurücksetzen (PR 4b, Schalter `E2EE_PW_BACKUP`)

Rückweg für Ausgesperrte und für alle, die ihr Passwort vergessen haben. **Nur mit `E2EE_PW_BACKUP=true`:** ohne Schalter gibt es die Routen nicht (`404 not_found`); die Ereignisliste und der Komplett-Reset (`POST /members/:id/reset`) bleiben. Alle Wege setzen **nur das Passwort** neu (Eingabe immer als `authKey`, nie Klartext) und ändern nie einen Schlüssel: Authenticator (TOTP), Passkeys und Wiederherstellungs-Codes bleiben, der Server kann keinen Personenschlüssel neu verpacken (er kennt weder Passwort noch `kek`).

| Methode, Pfad | Rolle | Beschreibung |
| --- | --- | --- |
| `POST /members/:id/password-reset` | admin, Step-up | `{ hours? (1–168, Standard 24), pin? (bool) }` → `{ invite: { id, token, link, pin?, expiresAt, requireApproval } }`: Einmal-Link „neues Passwort“ für ein **anderes** Mitglied der eigenen Familie (Einladung `kind = password_reset`). Eigene ID: `409 cannot_reset_self` (der Admin umgeht so nicht seinen eigenen zweiten Faktor); fremde oder unbekannte ID `404`; Konto ohne Passwort `409 no_password`, ohne TOTP `409 no_second_factor`, gesperrt oder wartend `409 not_active`. Ein neuer Link ersetzt einen offenen früheren. Das Konto bleibt bis zum Einlösen **unverändert nutzbar** (Sitzungen, altes Passwort; ein ungenutzter Link sperrt nie aus). Die Person wird sofort benachrichtigt (Push ohne Inhalt, Ereignis `password_reset_requested`). Audit `password_reset_requested` |
| `POST /auth/invites/password-reset/start` | ohne Anmeldung | `{ token, pin?, authKey }` (Token nur im Body) → `{ challengeId }`: prüft Link und PIN (wie jede Einladung: gezählt vor dem Vergleich, 5 Fehlversuche sperren) und merkt den Prüfwert des neuen `authKey`. Jeder ungültige Fall `400 invite_invalid`. Die Routen für neue Konten und Passkeys (`/auth/invites/password/start`, `/passkey/options`) lehnen einen solchen Link mit `400 invite_invalid` ab, umgekehrt auch ein Komplett-Reset-Link diese Route |
| `POST /auth/invites/password-reset/complete` | ohne Anmeldung | `{ challengeId, code, client?, device? }` → `{ member, status: "active", recoveryCodes: [], session }`: `code` ist ein **gültiger TOTP-Code der Person** (der vorhandene Authenticator; ein Wiederherstellungs-Code oder der Code eines anderen Kontos zählt nicht, falsch `400 invalid_code`, gezählt gegen Konto und IP). Link-Verbrauch, TOTP-Zeitschritt (Replay-Schutz) und neues Passwort in **einer** Transaktion; parallele Einlösungen: genau eine gewinnt |
| `POST /auth/password-reset/recovery` | ohne Anmeldung | `{ email, code (Wiederherstellungs-Code), authKey, client?, device? }` → `{ user, session, recoveryCodesRemaining }`: „Passwort vergessen?“ mit einem der 10 Codes (wird verbraucht, atomar in der Transaktion des Resets; scheitert der Reset, bleibt der Code gültig). Fehlerantwort, Sperren und Zähler wie bei `POST /auth/login/recovery` (`401 invalid_credentials` für falschen Code, unbekannte und gesperrte Konten gleich). Konto ohne Passwort `409 no_password` |
| `POST /auth/password-reset/passkey` | ohne Anmeldung | `{ email, challengeId, response, authKey, client?, device? }` (Challenge von `POST /auth/login/passkey/options`) → wie oben: „Passwort vergessen?“ mit einem Passkey. Die E-Mail muss zum Konto des Passkeys gehören (`409 email_mismatch`): der Salt der Ableitung hängt an der E-Mail, ein anderes Passwort könnte nie zur Anmeldung dienen |
| `GET /me/security-events` | alle | `{ events: [{ id, kind, via, actorName, byAdmin, createdAt }] }`: die **eigenen** Sicherheitsereignisse, neueste zuerst, höchstens 50, nie Inhalte oder IP. `kind`: `password_reset_requested` (Admin hat einen Link erstellt), `password_reset_done`, `account_reset_requested` (Komplett-Reset); `via`: `admin`, `recovery_code`, `passkey`; `actorName` der auslösende Admin (sonst `null` = du selbst). Aufbewahrung ein Jahr |

**Nie mit TOTP allein, nie per E-Mail-Link ohne zweiten Nachweis.** „Passwort vergessen?“ verlangt einen Wiederherstellungs-Code oder einen Passkey; der Admin-Link verlangt zusätzlich den TOTP-Code der Person. Der Wiederherstellungs-Code ist schon ohne den Reset ein vollwertiger Anmeldeweg (`POST /auth/login/recovery`), der Reset gibt ihm keine zusätzliche Macht.

**Wirkung (eine Transaktion, `applyPasswordReset`):** altes Passwort widerrufen, neues mit `authKey` anlegen (Platzhalter im Klartext-Hash, Klartext-Anmeldung nicht mehr möglich, wie beim Passwortwechsel), offene Reset-Links der Person widerrufen, **alle Sitzungen, Refresh-Familien und Geräte der Person beenden** (WebSockets schließen, Push-Endpunkte werden gelöscht), Ereignis `password_reset_done` und Audit `password_reset_done` schreiben; danach stellt der Server die neue Sitzung aus. **Passwort-Sicherung des Schlüssels:** die aktuelle Zeile (`active`) wird `stale` (**nie gelöscht**), eine unbestätigte (`pending`) `superseded`; `GET /me/key-backup-pw` liefert sie weiter mit `state: stale` (mit dem alten Passwort bleibt sie lesbar). Die App legt auf einem Gerät mit Personenschlüssel danach selbst eine neue Sicherung an (`PUT`, Round-Trip, `verified`): die `stale`-Zeile wird dabei `superseded`. Der Wiederherstellungsschlüssel und die QR-Übertragung gelten unverändert. Auch ein Komplett-Reset (`POST /members/:id/reset`) setzt die Sicherung beim Neu-Einrichten auf `stale`.

**Benachrichtigung:** Bei jedem Reset (`password_reset_requested`, `password_reset_done`, Komplett-Reset) liest der Server **vor** dem Widerruf die Push-Themen der aktiven Geräte der Person und weckt sie danach ohne Inhalt (fester Wecker, kein Text, kein Hinweis auf den Anlass; `PushService.weckeThemen`). Die App holt daraufhin `GET /me/security-events` und meldet Neues lokal:
- *Vordergrund:* Dialog „Sicherheitshinweis“ (bleibt, bis er bestätigt ist).
- *Hintergrund:* lokale Benachrichtigung auf dem **eigenen Kanal „Sicherheit“** (hohe Wichtigkeit, nie der Chat-Kanal) mit festem Text „An deinem Konto hat sich etwas geändert“ (nie Namen); Tippen öffnet Profil > Sicherheitsereignisse. Der Stand „gemeldet bis“ (`sicherheitSeit`) rückt erst vor, wenn die Benachrichtigung wirklich angezeigt wurde; sonst holt der nächste Start der App es nach.
- *Sitzung durch den Reset widerrufen:* Kommt der Wecker, die Abfrage scheitert aber mit „Sitzung abgelehnt“ obwohl das Zugangstoken laut Uhr noch gilt, zeigt die App „Du wurdest abgemeldet. Dein Passwort wurde zurückgesetzt …“ und merkt sich einen dauerhaften Hinweis (Banner auf der Anmeldeseite, Dialog nach dem Anmelden, bis bestätigt). Ein schlicht abgelaufenes Zugangstoken löst das nie aus. Grenze: Dieselbe Abfolge entsteht auch, wenn das Gerät auf andere Weise abgemeldet wurde (zum Beispiel „überall abmelden“); der Text sagt dann bewusst „melde dich mit einem Wiederherstellungscode an, wenn du das nicht warst“.
- Weckrufe prüfen höchstens alle 5 Minuten, der Start der App immer.
Ohne Push bleibt die Ereignisliste im Profil.

**Raten am Link:** Falsche TOTP-Codes am Reset-Link zählen am Link selbst (gemeinsamer Zähler mit der PIN): nach 5 Fehlversuchen ist er gesperrt (`locked_at`, Audit `invite_locked` mit `reason: totp`); der Admin erzeugt einen neuen. Zusätzlich gelten die Sperren (IP, Konto, Paar).

**Veraltete Sicherung:** `GET /me/keys` enthält `pwBackupStale: true` (sonst fehlt das Feld), solange die aktuelle Passwort-Sicherung veraltet ist; die App bietet dann auf einem Gerät mit Schlüssel „Sicherung erneuern“ an, ohne die protokollierte Sicherung selbst abzurufen. Die `stale`-Zeile bleibt **bewusst mit Step-up abrufbar** (`GET /me/key-backup-pw`, `state: stale`), damit jemand, der sein altes Passwort noch kennt, den Verlauf zurückholen kann; Risiko und Begründung in `PROJEKTBESCHREIBUNG.md` 9a.

**Rollout-Hinweis:** Der Link „neues Passwort“ funktioniert nur mit `authKey` (App ab dieser Version); eine alte App zeigt den Update-Hinweis, sie schickt nie Klartext. Auch bei ausgeschaltetem Klartext-Stichtag (`AUTH_LEGACY_PASSWORD_LOGIN=false`) ist der Reset der Rückweg für Ausgesperrte: Wer sein Passwort vergessen hat, bekommt einen Link vom Admin oder nutzt „Passwort vergessen?“; es braucht dafür keinen alten Klartext-Weg.

**Fehlercodes neu:** `409 cannot_reset_self`, `409 no_second_factor`, `409 not_active`, `409 email_mismatch`.

## Sync `POST /api/v1/sync`

Der Abgleich der Familiendaten (Phase 1c; erster Fachbereich: **Listen**). Gleiche Anmeldung wie `/me` (Cookie + `X-CSRF-Token` oder `Authorization: Bearer`). **Die Familie und die Rolle kommen immer aus der Sitzung, nie aus dem Körper**; ein Feld `familyId` im Körper führt zu `400`. Konzept und Entscheidungen: `PROJEKTBESCHREIBUNG.md`, Abschnitt 6.

**Anfrage** (alle Objekte sind `strict`: unbekannte Felder im Umschlag führen zu `400 invalid_request`)

```json
{
  "protocolVersion": 1,
  "deviceId": "<Geräte-ID der Sitzung>",
  "sinceRev": 17,
  "limit": 500,
  "snapshotRev": 40,
  "ops": [
    { "opId": "<UUID>", "op": "upsert", "entity": "list_item", "id": "<UUID>", "baseRev": 12,
      "fields": { "text": "Hafermilch", "doneAt": "2026-10-19T10:00:00.000Z" } },
    { "opId": "<UUID>", "op": "delete", "entity": "list", "id": "<UUID>", "baseRev": 3 }
  ]
}
```

- `protocolVersion`: Version, die der Client spricht (Ganzzahl ab 1). Ist sie kleiner als `minProtocolVersion` (`GET /api/v1/version`, Einstellung `MIN_PROTOCOL_VERSION`), antwortet der Server mit `426 update_required`; die App zeigt dann die Pflicht-Update-Seite.
- `deviceId`: muss die Geräte-ID der Sitzung sein (`session.deviceId` aus der Anmeldung bzw. `/me`), sonst `409 device_mismatch` (die App lädt dann `/me` neu).
- `sinceRev`: letzte Revision, die der Client vollständig kennt (`0` = nichts, der Server liefert den Snapshot). Der Server merkt sie als `devices.last_rev`.
- `limit` (optional, 1 bis 500, Standard 500): Protokolleinträge je Antwortseite (ersetzte Stände werden übersprungen, die Seite kann daher weniger `changes` enthalten).
- `snapshotRev` (optional): nur in den Folgeanfragen eines mehrseitigen Snapshots, genau der Wert aus der Antwort der ersten Seite (siehe unten). Dann ist `sinceRev` der Cursor.
- `ops`: höchstens **50** je Aufruf, in der Reihenfolge ihrer Entstehung. Der Körper ist höchstens **1 MB** groß (sonst `413 payload_too_large`).
- Je Op: `opId` (vom Client vergebene UUID, macht den Upload wiederholbar), `op` (`upsert` oder `delete`), `entity`, `id` (vom Client vergebene UUID), `baseRev` (Revision des Datensatzes, auf der die Änderung aufbaut; `0` = neu angelegt) und bei `upsert` die **geänderten** Felder in `fields`. Eine Op mit unbekanntem Feld, falschem Wert, zu langem Text oder ungültigen Zeichen (NUL, einzelnes Surrogat) wird als `invalid` abgelehnt, ohne die anderen Ops zu blockieren. Fehlt die `opId` oder ist sie keine UUID, ist die ganze Anfrage ungültig (`400`).

**Antwort** (immer `200`, wenn die Anfrage gültig und die Person angemeldet ist)

```json
{
  "status": "ok",
  "rev": 21,
  "acked": ["<opId>", "..."],
  "rejected": [{ "opId": "<UUID>", "code": "deleted" }],
  "conflicts": [{ "opId": "<UUID>", "entity": "list_item", "id": "<UUID>", "fields": { "text": "Milch" }, "serverRev": 19 }],
  "changes": [
    { "rev": 18, "entity": "list", "id": "<UUID>", "tombstone": false, "fields": { "name": "Einkauf", "kind": "shopping", "audience": "family", "ownerId": "<UUID>", "createdAt": "2026-10-19T08:00:00.000Z" } },
    { "rev": 19, "entity": "list_item", "id": "<UUID>", "tombstone": true, "fields": {} }
  ],
  "hasMore": false,
  "next": 21,
  "snapshotRev": 21,
  "serverTime": "2026-10-19T10:00:01.000Z"
}
```

- `status`: `ok` oder `resync_required` (siehe unten). `rev`: aktueller Stand der Familie zum Zeitpunkt der Abfrage.
- `acked`: Ops, die der Server übernommen hat (auch ohne Wirkung, z. B. gleicher Wert; auch **mit Konflikten**: die nicht umstrittenen Felder wurden übernommen) und die er bei einem wiederholten Upload erneut bestätigt. `rejected`: Ops, die nicht angewendet wurden, mit Grund (Tabelle unten). Der Client nimmt beide aus seinem Ausgang.
- `conflicts`: Felder einer Op, die **nicht** übernommen wurden, weil sie seit `baseRev` anderswo geändert wurden; `fields` nennt den **Serverstand** dieser Felder, `serverRev` die Revision des Datensatzes. Der Client übernimmt den Serverwert (und weist die Person darauf hin).
- `changes`: Änderungen seit `sinceRev`, **stabil nach `rev` sortiert**, höchstens `limit` Einträge je Seite. Geliefert wird jeweils der **aktuelle Stand** des Datensatzes (nur der letzte Eintrag je Datensatz; `fields` enthält alle Felder), bei `tombstone: true` ohne Inhalt. Mit `hidden: true` verschwindet der Datensatz nur für diese Person (Freigabe zurückgenommen), der Client entfernt ihn lokal. Bei `sinceRev: 0` (Snapshot) gibt es keine Tombstones. Auch ein **gelöschter** Datensatz, den die Person nicht (mehr) sehen darf, kommt (nur im Delta, `sinceRev > 0`) als `hidden`-Tombstone: eine Liste, die erst für die Person unsichtbar gemacht und dann gelöscht wurde, bliebe sonst als Geist in ihrer App stehen. Das verrät die ID eines gelöschten, nie sichtbaren Datensatzes (nie Inhalt; siehe Datenschutz-Entwurf). Die eigenen Änderungen des Geräts kommen ebenfalls zurück (so lernt der Client die neue Revision des Datensatzes).
- `hasMore` / `next`: gibt es mehr als `limit` Änderungen, ist `hasMore` `true` und `next` das `sinceRev` der nächsten Anfrage (ohne Ops). Sonst gilt `rev` als neues `sinceRev`. Ops werden nur in der ersten Anfrage gesendet.
- **Mehrseitiger Snapshot (`snapshotRev`):** Die erste Seite (`sinceRev: 0`) legt die Ziel-Revision fest (Stand der Familie) und nennt sie als `snapshotRev`, solange weitere Seiten folgen. Der Client sendet sie mit `sinceRev: next` zurück. Folgeseiten prüfen **nie** gegen `purged_rev` (ein Snapshot braucht keine Tombstones, Bereinigung während des Laufs kann ihn nicht brechen), liefern nur Einträge bis zur Ziel-Revision, **nie Tombstones** und schreiben `devices.last_rev` nicht fort. Ist die letzte Seite erreicht und die Familie inzwischen weitergekommen, antwortet der Server mit `hasMore: true`, `next` = Ziel-Revision und **ohne** `snapshotRev`: der Client fährt mit einem normalen Lauf ab dort fort (Änderungen während des Snapshots kommen als Delta). Ein `snapshotRev` über dem Stand der Familie ergibt `resync_required`; ein `snapshotRev` kleiner oder gleich `sinceRev` wird ignoriert. Der Client speichert `snapshotRev` mit dem Cursor (ein unterbrochener Snapshot wird fortgesetzt) und löscht es bei `resync_required`, Gerätewechsel und Abschluss.
- **`resync_required`**: Der Client ist zu weit zurück (`sinceRev` liegt vor `families.purged_rev`: Tombstones bzw. Protokolleinträge wurden schon bereinigt; gilt nicht für Folgeseiten eines Snapshots), ihm eilt die Datenbank voraus (`sinceRev` größer als der Stand des Servers, z. B. nach einem Zurückspielen) oder seine Sicht hat sich geändert (`devices.resync_required`, gesetzt beim Rollenwechsel der Person; das Gerät kennt Datensätze, die es jetzt nicht mehr sehen dürfte). Das Flag gilt, bis das Gerät mit `sinceRev: 0` neu beginnt (und die Rolle seither unverändert ist). Die Antwort enthält keine `changes`; die mitgesendeten Ops sind trotzdem angewendet und bestätigt. Der Client leert die lokalen Fachtabellen (der Ausgang bleibt) und beginnt mit `sinceRev: 0` von vorn.
- Der Aufruf ändert `devices.last_rev` (auf das gesendete `sinceRev`, nicht bei Folgeseiten eines Snapshots) und `last_seen_at` des Geräts.

**Entscheidungen**

- **Idempotenz:** Jede Op läuft in einer eigenen Transaktion; die `opId` wird in `applied_ops` gespeichert (mit Ergebnis, Ziel der Op und den **Namen** der Konfliktfelder, nie mit Werten). Eine wiederholte Op (Antwort ging verloren) erhöht die Revision nicht und liefert dasselbe Ergebnis; Konfliktwerte werden dabei neu gelesen und die Rechte neu geprüft (wer den Datensatz inzwischen nicht mehr sehen darf oder wenn er gelöscht ist, bekommt keine Werte). Eine `opId`, die von einem **anderen Gerät** stammt, wird mit `duplicate_op` abgelehnt. `applied_ops` wird nach 90 Tagen bereinigt, **abgelehnte** Ops schon nach 7 Tagen.
- **Revisionen:** je Familie fortlaufend und lückenlos (die Familienzeile wird je Op gesperrt, `families.current_rev` atomar fortgeschrieben; gleichzeitige Syncs laufen nacheinander). Jede Änderung schreibt einen Eintrag in `change_log` und setzt `field_revs` je geänderten Feld.
- **Konflikte, Last-write-wins pro Feld:** Ein Feld einer `upsert`-Op **verliert**, wenn seine `field_rev` größer als `baseRev` ist (jemand hat es seit der Basis des Clients geändert) und diese Änderung **nicht vom selben Gerät** stammt. Der Serverwert bleibt und steht in `conflicts`. Reihenfolge bestimmt der Server, nie die Uhr des Clients. Felder, die nur eine Seite geändert hat, werden zusammengeführt (Abhaken gewinnt nicht gegen gleichzeitiges Umbenennen). Ein gleicher Wert ist kein Konflikt. Mehrere Ops desselben Geräts mit gleichem `baseRev` kollidieren nicht miteinander.
- **Löschen gewinnt:** `delete` wirkt immer (auch gegen gleichzeitige Änderungen) und ist wiederholbar. Ein `upsert` auf einen gelöschten Datensatz wird mit `deleted` abgelehnt. Das Löschen einer Liste löscht ihre Einträge mit (je ein Tombstone, die der Einträge mit kleineren Revisionen). Beim Löschen werden Inhalte sofort überschrieben und im `change_log` geleert.
- **Anlegen:** `upsert` auf eine unbekannte `id` mit `baseRev: 0` legt an (Pflichtfelder nötig); mit `baseRev > 0` ist der Datensatz inzwischen bereinigt (`not_found`). Eine ID, die schon einem fremden Datensatz (auch einer anderen Familie) gehört, ergibt `not_found` (verrät nicht, dass es sie gibt).
- **Verweise:** Verweise auf Mitglieder (`assigneeId`) müssen auf ein **aktives Mitglied der eigenen Familie** zeigen (`invalid_reference`), `listId` auf eine vorhandene, sichtbare, nicht gelöschte Liste.
- **Sortierung:** `position` ist eine Kommazahl; eine neue Position liegt zwischen den Nachbarn (Mittelwert, neue Einträge oben: kleiner als alle offenen). Nur das verschobene Feld ändert sich; Gleichstand entscheidet die Anlegezeit, dann die ID. Wertebereich ±10^12.
- **Obergrenzen:** 200 lebende Listen je Familie, 1000 lebende Einträge je Liste, 5000 lebende Termine je Familie und zusätzlich **500 lebende Termine je Besitzer für Kinder** (ein Kinderkonto kann die Familienobergrenze nicht allein füllen), 50 Teilnehmer und 500 Ausnahmen je Termin (`limit_reached`).
- **Mitglied entfernen:** Verweise der Person (`assigneeId`, `ownerId`) werden mit einem Änderungseintrag auf `null` gesetzt und die Geräte per WebSocket benachrichtigt; Mitglieder selbst sind keine Sync-Entität.
- **Wartung** (stündlich): Tombstones werden entfernt, wenn alle aktiven (nicht abgemeldeten) Geräte der Familie sie kennen (`last_rev` >= Revision) oder sie älter als 90 Tage sind; dabei steigt `families.purged_rev`. Ersetzte Protokolleinträge verschwinden nach 90 Tagen. Gerät mit neuer Geräte-ID (neue Anmeldung): die App beginnt mit einem Snapshot.
- **Limits:** höchstens 120 Aufrufe je Minute und IP (`SYNC_RATE_LIMIT_MAX`), **50 Ops** je Aufruf, 1 MB. Zusätzlich ein Token-Bucket **je Gerät** und **je Person** (Person = Dreifaches): Anfragen (`SYNC_REQ_BURST` 30, `SYNC_REQ_PER_MINUTE` 120) und Ops (`SYNC_OPS_BURST` 100, mindestens 50, `SYNC_OPS_PER_MINUTE` 120; eine Anfrage kostet 1, jede Op 1) sowie eine Tagesobergrenze je Gerät (`SYNC_OPS_PER_DAY`, 5000 Ops in 24 Stunden, gezählt über `applied_ops`). Reicht der Bucket nicht, wird die **ganze** Anfrage mit `429 rate_limited` und `Retry-After` abgewiesen (nichts wird halb verarbeitet; der Client wiederholt später dieselben Ops). Jede Op läuft mit `lock_timeout` (5 s) und `statement_timeout` (10 s); wird die Sperre der Familie nicht rechtzeitig frei oder dauert die Anweisung zu lange, antwortet der Sync mit `503 server_busy` und `Retry-After` (die Op ist dann nicht angewendet). Inhalte werden nie geloggt.

**Gründe einer Ablehnung (`rejected[].code`)**

| Code | Bedeutung |
| --- | --- |
| `invalid` | Eingabe ungültig: unbekanntes Feld, falscher Typ oder Wert, zu lang, ungültige Zeichen, Pflichtfeld fehlt, unveränderliches Feld (`listId`, `terminId`, `userId`, `originalStart`) geändert, Server-Feld (`ownerId`, `createdAt`) gesendet; bei Terminen außerdem unstimmige Zeiten (Ende vor Beginn, fehlende Zeitzone), unbekannte Zeitzone, unzulässige Wiederholungsregel; ein zweiter aktiver Teilnehmer/eine zweite Ausnahme für dasselbe Ziel ergibt `not_found` |

| `parent_deleted` | Die übergeordnete Liste bzw. der übergeordnete Termin wurde gelöscht |

**Rechte (zentrales Modell, `server/src/sync/permissions.ts`)**

**Termine (Phase 1c-2a)**

- **Zeitmodell:** Die Familienzeitzone ist fest `Europe/Berlin` (Anzeige und Tagesgrenzen). **Zeittermine** (`ganztaegig: false`) speichern Beginn und Ende als Zeitpunkte (`startUtc`, `endUtc`, ISO-8601, in der Antwort UTC mit Millisekunden) plus IANA-Zeitzone (`tzid`); Wiederholungen werden in der **Wanduhrzeit der `tzid`** gerechnet (10 Uhr bleibt über die Zeitumstellung 10 Uhr). **Ganztägige Termine** (`ganztaegig: true`) sind Kalendertage ohne Uhrzeit und Zeitzone: `startDate`, `endDate` als `YYYY-MM-DD`, das **Ende ist exklusiv** wie in iCalendar (ein Tag: Ende = Folgetag). Der Server prüft die Stimmigkeit nach dem Zusammenführen jeder Änderung (Zeittermin: Beginn, Ende >= Beginn und `tzid`; ganztägig: Ende > Beginn), sonst `invalid`. Felder der jeweils anderen Art dürfen als Rest stehen bleiben; maßgeblich ist `ganztaegig`.
- **Zeitzonen-Kennung:** `tzid` muss der Laufzeit des Servers bekannt sein und in der Schreibweise der IANA-Datenbank stehen (`Europe/Berlin`; `europe/berlin` wird abgelehnt, weil die Zeitzonen-Datenbank der App Groß-/Kleinschreibung unterscheidet). Ältere Namen (z. B. `Asia/Kolkata`) bleiben erlaubt; kennt die App eine Kennung nicht, rechnet sie in der Familienzeitzone.
- **Wiederholung:** `rrule` ist RFC-5545-Text **ohne** Präfix. Erlaubt: `FREQ` (`DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY`), `INTERVAL` 1 bis 999, `COUNT` 1 bis 1000 oder `UNTIL` (nicht beide; Zeittermin: `YYYYMMDDTHHMMSSZ` in UTC, ganztägig: `YYYYMMDD`), `BYDAY` (bei `MONTHLY`/`YEARLY` mit Zahl -5 bis 5), `BYMONTHDAY`, `BYMONTH`, `BYSETPOS`, `WKST`; höchstens 300 Zeichen und 10 Teile. Abgelehnt: **unerfüllbare Kombinationen** (`BYMONTH` mit `BYMONTHDAY`, für die es keinen Monat mit passendem Tag gibt, z. B. 30. Februar oder 31. April), `SECONDLY`/`MINUTELY`/`HOURLY`, `BYHOUR`/`BYMINUTE`/`BYSECOND`/`BYYEARDAY`/`BYWEEKNO`, ein Präfix, Kleinbuchstaben, doppelte Teile. Die Prüfung ist ein Hand-Tokenizer (`server/src/sync/rrule.ts`, kein regulärer Ausdruck mit Rückverfolgung). Der **Client** expandiert (Paket `rrule` mit `timezone`): höchstens 1000 Vorkommen je Termin und Abfrage, Horizont 5 Jahre.
- **Ausnahmen** (`termin_ausnahmen`): eine Zeile je (`terminId`, `originalStart`); `originalStart` ist **unveränderlich** und nennt das ursprüngliche Vorkommen: bei Zeitterminen den Beginn in UTC (`YYYY-MM-DDTHH:MM:SSZ`, der Server normalisiert), bei ganztägigen den Tag (`YYYY-MM-DD`). `abgesagt` blendet das Vorkommen aus; `titel`, `start`, `ende`, `ort` überschreiben (`null` = unverändert; nur `start` gesetzt: die Dauer bleibt; `start`/`ende` haben die Art von `originalStart`). Eine Ausnahme wird nicht gelöscht, sondern zurückgesetzt (alles leer); die App vergibt ihre ID aus Termin und `originalStart` (zwei Geräte schreiben dieselbe Zeile; ein zweites Anlegen mit neuer ID wird abgelehnt). **Gelöscht wird eine Ausnahme nie von der App** (nur zurückgesetzt oder mit dem Termin per Kaskade): eine gelöschte feste ID bliebe als Tombstone stehen und ließe sich nicht wiederverwenden (`deleted`). **„Dieses und alle folgenden“** ändert die Serie nicht über Ausnahmen: der Master bekommt ein `UNTIL` vor dem **ursprünglichen** Beginn des Vorkommens (nicht vor einem durch eine Ausnahme verschobenen), ab dort beginnt ein neuer Termin. Der neue Termin gehört der Person, die ihn anlegt (der Server setzt `ownerId` aus der Sitzung): teilen Eltern die Serie eines Kindes, ändert das Kind den neuen Teil nicht mehr.
- **Teilnehmer** (`termin_teilnehmer`): eine Zeile je Person (`userId` aktives Mitglied der Familie, `terminId`, beide unveränderlich); eine aktive Zeile je Person und Termin (ein zweites Anlegen ergibt `not_found`), Entfernen = Tombstone, danach ist Neu-Eintragen möglich. Verlässt die Person die Familie, wird ihre Zeile **mit Tombstone und Änderungseintrag** gelöscht (`memberOwned` im Register, vor dem Entfernen der Mitgliedschaft); die Zeile selbst verschwindet danach per Fremdschlüssel-Kaskade, der Änderungsstrom liefert den Tombstone trotzdem (`hidden`, nur die ID), und die Wartung räumt den verwaisten Eintrag nach 90 Tagen.
- **Erinnerung:** `erinnerungMin` (Minuten vor Beginn, 0 bis 40320, `null` = keine) wird gespeichert und synchronisiert; die Benachrichtigung entsteht lokal auf dem Gerät (Android, `flutter_local_notifications`), der Server verschickt nichts (siehe PROJEKTBESCHREIBUNG, Abschnitt 6b).

**Chat (Phase 1c-3a)** · Konzept, Rechte und Datenschutz: `PROJEKTBESCHREIBUNG.md`, Abschnitt 6c.

- **Sichtbarkeit:** Direkt- und Gruppenchats (`konversation` mit `art` `direct`/`group`) sehen **nur ihre Teilnehmer**, auch Admin und Eltern nicht; Nachrichten und Lesestände erben das. Für alle anderen existiert die ID nicht: Ändern, Löschen und Anlegen darunter ergeben `not_found` (auch mit IDs einer fremden Familie), der Änderungsstrom liefert nichts, auch keinen Tombstone. Der Familienchat (`art` `family`, genau einer je Familie) gehört allen aktiven Mitgliedern. Wer aus einer Gruppe entfernt wird (`teilnehmer` geändert), bekommt einen `hidden`-Tombstone der Konversation (die App entfernt sie samt Nachrichten und Lesestand); wer nie dabei war, nichts.
- - **Inhalt ist undurchsichtig und verschlüsselt (E2EE Phase 2):** `text` einer Nachricht ist in jeder neuen Konversation eine **verschlüsselte Hülle** `e1:` + Base64url (Aufbau und Verfahren: `PROJEKTBESCHREIBUNG.md`, Abschnitt 9a). Der Server prüft nur die **Form**: Präfix passend zur Konversation (`encVersion`), nur Base64url-Zeichen, mindestens 153 Zeichen (Kopf 114 Byte + Tag), höchstens 16 384 Zeichen; er entschlüsselt, prüft, loggt und indiziert nie etwas (kein Suchendpunkt, keine Vorschau). **Klartext `p1:` ist in einer `e1`-Konversation `invalid`** (Downgrade-Schutz); `p1` gilt nur für Altbestand (`encVersion` `p1`, nur lesbar, die App schreibt dort nicht mehr). `l1:` (lokaler Klartext im Ausgang der App) lehnt der Server ab. `titel` (Gruppenname) bleibt `p1:` + Klartext: der Name ist sichtbarer Metadatenwert (wie die Teilnehmerliste).
- **Familienchat anlegen:** `upsert konversation {art: "family"}` von jeder Rolle; ohne `titel` und `teilnehmer`; verschlüsselt (`encVersion` `e1` ist der Standard, ein Client kann `p1` nur für Altbestände senden). Die ID ist **vorgeschrieben**: SHA-256 von `lx-fampad:familienchat:<familyId>`, die ersten 16 Byte mit Version 5 und Variante 10xx als UUID (`server/src/sync/entities/chat-ids.ts`, gleich in der App); jede andere ID ist `invalid`. Dieselbe ID noch einmal ist eine Wiederholung ohne Wirkung. Danach ist er für Clients unveränderlich (`forbidden`) und nicht löschbar.
- **Direktchat:** `art: "direct"`, `teilnehmer` = genau die zwei Personen (anlegende Person dabei, nur aktive Mitglieder der Familie, sonst `forbidden` bzw. `invalid_reference`); die Liste wird sortiert und ohne Doppelte gespeichert. Je Paar ein Chat: die ID ist vorgeschrieben (`direkt:<kleinere Nutzer-ID>:<größere>`, kleingeschrieben und sortiert), jede andere ist `invalid`; dieselbe ID noch einmal ist ein Update ohne Änderung. Wurde der Chat gelöscht (Person entfernt), belebt ein erneutes Anlegen mit derselben ID ihn wieder. Unveränderlich, nicht löschbar.
- **Gruppe:** `art: "group"` (ID: Zufalls-UUID Version 4, abgeleitete IDs mit Nibble 5 sind reserviert), 2 bis 20 `teilnehmer` (anlegende Person dabei), `titel` optional. Jeder Teilnehmer ändert `titel` und `teilnehmer`; löschen darf nur die anlegende Person (`ownerId`). Bleiben nach dem Entfernen eines Mitglieds aus der Familie weniger als zwei Teilnehmer, wird die Gruppe gelöscht.
- **Nachrichten:** schreiben darf jede Person mit Sicht, `autorId` und Zeit setzt der Server. **Bearbeiten (nur `text`) und Löschen nur der Autor** (`forbidden`); Ausnahme: **Admins löschen im Familienchat auch fremde Nachrichten**, nie in privaten Chats. `bearbeitetAt` setzt der Server beim Ändern des Textes. `antwortAuf` (nur beim Anlegen) muss eine Nachricht **derselben Konversation** sein, sonst `invalid`; `text` muss mit der Hülle der Konversation beginnen (`encVersion` `e1:` oder, nur für Altbestand, `p1:`) und bei `e1` die Form einer verschlüsselten Hülle haben, sonst `invalid`. Beim Bearbeiten wird ältere Text-Fassung aus dem Protokoll entfernt. Mengenbegrenzung: höchstens 60 neue Nachrichten und 60 Text-Änderungen je Person und Minute, Text je Person höchstens 1 MiB je Stunde und 4 MiB je Tag, 20 000 lebende Nachrichten je Konversation, 10 Teilnehmerwechsel je Person und Minute (`limit_reached`).
- **Lesestand:** eine Zeile je Person und Konversation (`userId` muss die eigene sein), `gelesenBis` = Zeit (`createdAt`) der letzten gelesenen fremden Nachricht. Schreiben nur die eigene Zeile, **lesen alle Teilnehmer der Konversation** (Lesebestätigung; Familienchat: alle Mitglieder); die ID ist vorgeschrieben (`lesestand:<Konversation>:<Person>`), jede andere ist `invalid`. `gelesenBis` geht nie zurück (ein kleinerer Wert wird verworfen). Die Teilnehmer erfahren per WebSocket von Änderungen (kein Push-Wecker).
- **Obergrenzen:** 500 lebende Konversationen je Familie, 100 je anlegender Person (`limit_reached`).
- **Mitglied entfernt:** aus Teilnehmerlisten genommen; Direktchats und Gruppen mit weniger als zwei Übrigen mit Tombstone gelöscht; `autorId` der Nachrichten wird `null`; Lesestand der Person wird gelöscht (Tombstone).
- **WebSocket:** `rev N` zu privaten Chats geht nur an die Teilnehmer (nach Person), zum Familienchat an alle Rollen mit Sicht.

**Epochen und Schlüssel-Wraps (E2EE Phase 2)** · Protokoll: `PROJEKTBESCHREIBUNG.md`, Abschnitt 9a. Zwei weitere Sync-Entitäten, Kinder der Konversation. Der Server speichert nur undurchsichtige
Base64url-Texte und wertet sie **nie** aus (keine Signaturprüfung, kein Entschlüsseln); er prüft Form, Größe, Eindeutigkeit und die Sicht. Nur in `e1`-Konversationen (sonst `invalid`).

- **`epoche`:** je (Konversation, Epoche) genau eine Zeile mit **vorgeschriebener ID** (`epoche:<Konversation>:<Nummer>`, SHA-256 mit Präfix `lx-fampad:`, Muster UUID Version 5, `chat-ids.ts`/`chat_ids.dart`); jede andere ID ist `invalid`.
  **Der erste Schreiber gewinnt:** wer eine schon vorhandene Epoche mit anderem Inhalt anlegt, wird mit `invalid` abgelehnt (die identische Wiederholung wird bestätigt); der Verlierer einer gleichzeitigen Rotation übernimmt
  die Epoche des Gewinners aus dem Änderungsstrom. Lückenlos: Epoche N gibt es erst, wenn N-1 da ist (sonst `invalid`). Alle Teilnehmer der Konversation lesen sie (im Familienchat alle aktiven Mitglieder), Nichtteilnehmer erfahren nichts
  (`not_found`, auch für Admins); unveränderlich, nicht löschbar (verschwindet nur mit der Konversation). Höchstens 1000 je Konversation, 20 neue je Person und Minute (`limit_reached`).
- **Grenzen für Epochen und Wraps:** Epochen je Person höchstens 3 je Minute und 12 je Stunde, höchstens 100 lebende je Konversation und Person (insgesamt 1000); Wraps höchstens 100 je Minute und 800 je Stunde, 2000 lebende je Konversation und Person (`limit_reached`). Wraps der **höchsten** Epoche nimmt der Server nur vom Verteiler dieser Epoche an (`forbidden`); für ältere Epochen (Verlauf teilen) darf jedes Mitglied Wraps anlegen. Eine gelöschte Epoche oder ein gelöschter Wrap lässt sich mit derselben ID wieder anlegen (Wiederbeleben). Im Verlauf für neu Aufgenommene liefert der Server die eigenen Wraps immer (Abfrage nach Empfänger, kein Verdrängen durch fremde Zeilen). Wraps und Lesestand lösen keinen Push-Wecker aus.
- **`epoche_wrap`:** der für **eine Person** verpackte Epochenschlüssel (Sealed Box plus Signatur des Verteilers). Je (Konversation, Epoche, Empfänger) ohne Schlüsselversion genau eine Zeile mit vorgeschriebener ID, der erste gewinnt
  (ein zweiter ist `not_found`, "gibt es schon"), unveränderlich. **Ohne `keyVersion`** (Altbestand und Apps bis 0.7.0) gilt die ID v1 `wrap:<Konversation>:<Nummer>:<Empfänger>`, **mit `keyVersion`** (Wrap-ID v2, „Verlauf freigeben“ und „Verlauf teilen“; nur mit dem Server-Schalter `E2EE_WRAP_KEY_VERSION=true` (Standard aus, sonst `invalid`; erst einschalten, wenn alle Apps der Familie aktualisiert sind: Apps bis 0.7.0 nehmen bei mehreren Wraps derselben Epoche den letzten); `GET /version` meldet `features.wrapKeyVersion`) gilt die ID v2 `wrap2:<Konversation>:<Nummer>:<Empfänger>:<Schlüsselversion>:<Absender>` (der Absender ist der Akteur: jeder Absender hat seinen eigenen Platz, mehrere Absender können dieselbe Epoche für dieselbe Version verpacken, der Empfänger probiert alle durch; ein zweiter Wrap desselben Absenders ist `not_found`). So kann dieselbe ältere Epoche nach einem Schlüsselwechsel oder Reset der Person noch einmal für ihren **neuen** Schlüssel verpackt werden; die alten Zeilen bleiben unverändert (sie gehören zum alten Schlüssel, Archiv). Jede andere Kombination aus ID und `keyVersion` ist `invalid`, ebenso eine `keyVersion`, die die Person noch nicht hat (größer als ihre aktuelle Schlüsselversion), oder eine Person ohne Schlüssel. Der Server liest nichts aus dem Wrap: ob Wrap und Feld dieselbe Version nennen, prüft allein der Empfänger (er öffnet nur Wraps seiner aktuellen Version). **Nur der Empfänger liest seinen Wrap** (auch der Verteiler, die anderen Teilnehmer und Admins nicht), der WebSocket-Hinweis geht nur an ihn. Anlegen darf jeder Teilnehmer;
  die Epoche muss es geben, der Empfänger muss Teilnehmer sein (Familienchat: aktives Mitglied), sonst `invalid`. Verlässt die Person die Familie, verschwinden ihre Wraps (Tombstone für ihre Geräte). Höchstens 20 000 je Konversation, 400 neue je Person und Minute.

Der Migrationsstand liest `drizzle.__drizzle_migrations`: die Laufzeitrolle braucht dafür `USAGE` auf das Schema und `SELECT` (deploy/README, `einrichtung-auth.sh`); ohne Grant ist `applied` `null` und `grantMissing` `true`. Es gibt bewusst **keine** Routen zum Abmelden, Zurücksetzen oder Entfernen anderer Personen unter `/admin`: dafür gelten die vorhandenen Routen (`POST /members/:id/password-reset`, `DELETE /devices/:id` für die eigenen Geräte, …) mit ihren Rechten.

Eine **ausdrückliche Positivliste** (nie eine Schleife über die Konfiguration): Schalter (`E2EE_PW_BACKUP`, `AUTH_LEGACY_PASSWORD_LOGIN`, `WEATHER_ENABLED`, `NTFY` = nur „eingerichtet“, `OPERATOR_TLS_PROBE` = an/aus), Grenzen und Zeiten (Rate-Limits, Sync-Limits, WebSocket, Standort teilen `LOC_*`, Anmeldung, Aufbewahrung des Protokolls). `key` ist der Name der Umgebungsvariablen (oder eine feste Kennung wie `accessTokenTtl`), `PUBLIC_URL` nur als Herkunft (ohne Zugangsdaten, Pfad und Query). **Nie** Geheimnisse (`AUTH_SECRET_KEY`, `NTFY_TOKEN`, Datenbank-URLs, Netatmo-Zugangsdaten), Pfade, Adressen mit Zugangsdaten, Koordinaten, Stations-Kennungen oder Namen. Geändert wird nichts: die Konfiguration steht in `/etc/lx-fampad/env` und ändert sich nur per SSH (mit Neustart).
- **Wartungsmodus und Familienhinweis (Paket 2b)** (Tabelle `operator_settings`, eine Zeile je Familie): `GET /admin/settings` (Betreiber, ohne Step-up) → `{ maintenance: { active, since, until }, notice: { text, setAt, expiresAt } | null }` (`active` gilt nur, solange `until` nicht abgelaufen ist; ein abgelaufener Hinweis erscheint nicht mehr). `PUT /admin/maintenance` `{ active: boolean, untilMinutes?: Ganzzahl }` (**Step-up**, Audit `operator_maintenance_set` mit `from`/`to`/`until`) schaltet den Wartungsmodus. **Der Wartungsmodus hat immer ein Ende:** `untilMinutes` (1 bis 4320, also höchstens 72 Stunden) ist die Dauer ab jetzt, ohne Angabe gelten 72 Stunden; der Server rechnet das Ende mit **seiner** Uhr aus (nie eine Uhrzeit vom Gerät: ein Feld `until` wird abgelehnt). `active: false` zusammen mit `untilMinutes` ist ungültig. Ungültige Dauer: `400 invalid_duration`. `PUT /admin/notice` `{ text: string | null, expiresInMinutes?: Ganzzahl }` (**Step-up**, Audit `operator_notice_set` mit Länge und Ablauf, **nie dem Text**) setzt (`text`) oder löscht (`null`, dann ohne `expiresInMinutes`) den Familienhinweis; Ablauf als Dauer ab jetzt (1 Minute bis 90 Tage, Serveruhr). Text: Unicode NFC, getrimmt, 1 bis 280 Zeichen, eine Zeile, **reiner Text ohne Links**. Abgelehnt (`400 invalid_notice`): Steuer- und Zeilentrennzeichen, Richtungsumkehr, LRM/RLM, Null-Breite-Leerzeichen, Word Joiner, BOM, Combining Grapheme Joiner (U+034F), Hangul- und Khmer-Füllzeichen, leeres Braille-Muster (U+2800), Objekt-Ersatzzeichen (U+FFFC) und Tag-Zeichen (U+E0000 bis U+E007F). **Erlaubt** bleiben ZWJ (U+200D) und ZWNJ (U+200C) sowie Variationsselektoren (Familien-Emoji). Links (`400 notice_link`): Schema mit `://`, `www.` und Domain-artige Muster mit gängigen Endungen (zum Beispiel `lx-labs.dev`, `x.de`); normale Sätze mit Punkten bleiben möglich. Jedes Setzen ist eine neue Version (`setAt`): die App merkt sich je Gerät **und Person**, welche Version weggeklickt wurde. Beide `PUT` antworten wie `GET /admin/settings`.
- **Für alle Angemeldeten:** `GET /family-notice` (jede Sitzung, kein Betreiber nötig, mit dem allgemeinen Anfragelimit) → derselbe Aufbau wie `GET /admin/settings` (nur die Familie der Sitzung). Die App fragt beim Start der Oberfläche, bei der Rückkehr, nach einem Abgleich mit Wartung und danach alle 5 Minuten und zeigt Wartung und Hinweis als Banner. `GET /version` meldet zusätzlich `maintenance: boolean` (öffentlich, ohne Einzelheiten).
- **Wartungsmodus, Wirkung** (`operator/maintenance.ts`, `onRequest`-Haken vor allen Routen): Ist er an, antworten **schreibende Anfragen** (`POST`/`PUT`/`PATCH`/`DELETE`, darunter `POST /sync` und alle neuen Anmeldungen, Einladungen und der Passwort-Reset) mit `503` `{ error: 'maintenance', maintenance: true, message }` und `Retry-After` (höchstens 60 Sekunden, endet die Wartung früher, nur bis dahin), **ohne** Hinweis auf Konto oder Eingabe (alle Anmeldeversuche gleich, kein Orakel). **Weiter erreichbar:** alle `GET` (Lesen, `/me`), `/admin/*` (der Betreiber schaltet selbst wieder aus), `POST /auth/refresh`, `/auth/logout`, `/auth/logout-all`, `/auth/step-up/*` und `POST /ws-ticket` (bestehende Sitzungen bleiben). **Der WebSocket `/ws` läuft ebenfalls weiter** (Hinweise auf Änderungen, Mitglieder-Hinweise und **Standort teilen** `loc_*`: der Standort ist flüchtig, nur im Prozessspeicher, und wird nie gespeichert; die Wartung betrifft die Datenbank, nicht diesen Kanal). Unbekannte Routen bleiben `404`. **Sicherungen:** immer ein Ende (siehe oben, höchstens 72 Stunden, gilt von selbst); Notausgang auf dem Server ohne Anmeldung: `node dist/cli/operator.js maintenance off` (Audit `operator_maintenance_set` mit `via: 'cli'`); ist die Datenbank nicht lesbar, gilt der zuletzt bekannte Stand (nie „gesperrt ohne Grund“); schaltet der Betreiber, während der Zustand gerade neu gelesen wird, gilt nie der veraltete Lesevorgang (Zähler der Schaltungen). Der Zustand wird höchstens alle 2 Sekunden neu gelesen (das Schalten leert den Speicher sofort). Er gilt für den **ganzen Server** (er bedient genau eine Familie). Die App behandelt `maintenance` nicht als Fehler: Sync-Zustand „Wartung“, Änderungen bleiben im Ausgang, erneuter Versuch im festen Takt `Retry-After` plus 0 bis 30 Sekunden Zufall (also 60 bis 90 Sekunden, ohne das Hochschaukeln des Fehler-Backoffs).
- **Warnungen (Paket 2a)** `GET /admin/warnings` (ohne Step-up): `{ enabled (Warnungen dieses Betreibers an?), pushAvailable, checkedAt (letzte Prüfung dieses Prozesses), lastNotifiedAt (letzter Wecker der Familie), active: [{ kind: cert|backup|database|ntfy|disk|logins|key|nas_pull|nas_restore, since, count }] }` (je Art zusammengefasst, `count` = Anzahl, bei `key` die Zahl der Personen, `since` = die älteste); keine Namen, Pfade oder Inhalte. `PUT /admin/warnings` `{ enabled: boolean }` (**Step-up**, Audit `operator_warnings_set`) schaltet die Warnungen dieses Betreibers ein oder aus (Standard an; Spalte `operators.alerts_enabled`) → wie `GET`. **Prüfer** (`operator/monitor.ts`, Takt alle 5 Minuten, gestartet in `server.ts`): wertet dieselben Messungen und **dieselben Schwellen mit demselben exakten Alter** wie `/admin/status` aus: Zertifikat < 14 Tage (`cert`), letzter Sicherungserfolg älter als 36 Stunden laut zweiter Statusdatei (`backup`), Datenbank (`database`) oder ntfy (`ntfy`) nicht erreichbar, Platte > 85 % (`disk`), mehr als 20 fehlgeschlagene Anmeldungen in 15 Minuten (`logins`, Familie und Einträge ohne Familie), Schlüssel-Ampel einer Person rot (`key`, nur Personen mit Schlüssel). **Je Episode (das Problem besteht seit `since`) höchstens eine Warnung, nicht bei jedem Lauf; Rückkehr ohne Meldung. Als gemeldet gilt eine Episode nur, wenn wirklich gewarnt wurde:** wurde wegen der Entprellung noch nicht gewarnt, wird es nachgeholt, sobald sie abgelaufen ist (wiederkehrende Probleme, eine zweite rote Person, Ausschaltzeit des Schalters). **Je Art höchstens alle 6 Stunden** (alle Personen der Schlüssel-Ampel zählen als eine Art), „unbekannt“ (Messung nicht lesbar) warnt nie und ändert den Zustand nicht. **Karenz „key“:** eine rote Ampel einer Person, von der kein Gerät je einen Schlüsselstand gemeldet hat (`devicesReported` 0, ältere App), wird erst nach 7 Tagen gemeldet; meldet ein Gerät eine Version und die Person ist trotzdem rot, sofort. Die Anzeige bleibt rot. **Grenzen:** „Datenbank“ und „ntfy nicht erreichbar“ sind zuverlässig nur in der Ansicht sichtbar (der Wecker läuft über dieselbe Datenbank und dasselbe ntfy; es gelten dann Speicherstand und zuletzt bekannte Push-Themen); fällt der API-Dienst ganz aus, läuft kein Prüfer. Der Zustand steht in `operator_alert_state` (nach einem Neustart keine Wiederholung); ist die Datenbank nicht erreichbar, gelten Speicher und zuletzt bekannte Push-Themen. Der **Wecker** geht nur an die Geräte der Betreiber mit eingeschalteten Warnungen (`PushService.weckeThemen`), ist der feste Wecker ohne Inhalt (Body `wecker`, kein Titel, keine Tags); die App holt danach `GET /admin/warnings` und zeigt lokal „Betrieb: Hinweis – öffne Betrieb“. Jede Warnung steht im Protokoll als `operator_alert_<Art>` (Kategorie Änderungen, ohne Person und Inhalt).

Zählt nur nicht abgemeldete Geräte aktiver Mitglieder der Familie der Sitzung. **Stand eines Geräts** (`operator/update-status.ts`, rein): `inactive` (seit über 90 Tagen nicht gesehen, zählt nie als veraltet), `unknown` (keine lesbare Version), `below_min` (unter `MIN_APP_VERSION`), `outdated` (unter der Referenz), sonst `current`; ohne lesbare Referenz gibt es nie `outdated`, die Mindestversion gilt weiter. `GET /admin/members` (mit Step-up) ergänzt je Gerät `appState` (`current|outdated|below_min|inactive|unknown`, `null` bei Web und anderen Plattformen) und je Mitglied `devicesBehind` (Zahl der Android-Geräte mit `outdated` oder `below_min`). Ausstehende Systemupdates des Servers werden **nicht** angezeigt (der Dienst darf sie ohne Administratorrechte nicht lesen).
- **Backups (Paket 3, Teil A)** Feld `nas` von `GET /admin/status` (nur Betreiber, ohne Step-up): die Rückmeldung des **NAS** über die letzte Abholung (`pull`) und den letzten automatischen Wiederherstellungstest (`restore`). Der Server hält dafür keine Zugangsdaten zum NAS: das NAS schickt nach jedem Lauf eine kleine Statusdatei über einen zweiten SSH-Schlüssel mit erzwungenem Befehl (`deploy/backup/lx-fampad-nasstatus-empfang.sh`, Einrichtung `einrichtung-nasstatus.sh`, `docs/BACKUP-EINRICHTUNG-SCHRITTE.md` Abschnitt 11). Der Befehl nimmt von stdin höchstens 4 KB an, prüft jede Zeile (`schluessel=wert`, nur bekannte Schlüssel, Zahlen/Zeiten/`ok|fehler`/`ja|nein`, keine doppelten Schlüssel, Zeiten nicht in der Zukunft) und schreibt atomar `/var/lib/lx-fampad-nasstatus/nas.status` (Besitzer `lxnasstatus`, Gruppe `lx-fampad` darf nur lesen; ergänzt `received_epoch` mit der Uhr des Servers). Der API-Dienst liest die Datei (`OPERATOR_NAS_STATUS_FILE`, `off` schaltet ab) und wertet sie nochmals streng aus (`operator/nas-status.ts`): größer als 4 KB, NUL-Byte, ein Format- oder Wertfehler oder ein doppelter Schlüssel machen die **ganze** Datei ungültig (`invalid: true`, alles `unknown`, nie ein Alarm); unbekannte, gut geformte Schlüssel einer neueren Fassung werden ignoriert und nie angezeigt. `configured`: es gibt eine gültige Rückmeldung (sonst „nicht eingerichtet“); `receivedAt`: wann der Server sie bekam. `pull.state`: `ok` bis 36 Stunden seit dem letzten Erfolg, `warn` darüber, `error` über 72 Stunden oder bei gemeldetem Fehlschlag; `restore.state`: `ok` bis 10 Tage, `warn` darüber, `error` über 21 Tage oder bei Fehlschlag; ohne gemeldeten Test (oder ohne Rückmeldung) `unknown`. Die Zustände fließen in die Gesamtampel erst ein, wenn sie nicht `unknown` sind (Karenz bis zur Einrichtung: weder „unbekannt“ noch Warnung). Warnarten **`nas_pull`** (Abholung älter als 36 Stunden oder fehlgeschlagen) und **`nas_restore`** (Test älter als 10 Tage oder fehlgeschlagen) gelten wie alle Arten (je Episode eine Meldung, 6 Stunden Entprellung, „unbekannt“ warnt nie). **Grenze:** die Angaben stammen vom NAS und sind ein Hinweis mit Alter, kein Beweis (ein übernommenes NAS könnte „ok“ melden). Nie enthalten: Pfade, Dateinamen, Fehlertexte, Inhalte.

## Wetter `GET /api/v1/weather`

Messwerte einer öffentlichen Netatmo-Wetterstation in der Nähe. **Nur der Server ruft Netatmo ab** (nie ein Client); die Route liefert den zwischengespeicherten Stand an angemeldete Mitglieder (Sitzung nötig, sonst `401`; jede Rolle). Antworten sind wie alle API-Antworten `no-store`.

- **Ausgeschaltet** (`WEATHER_ENABLED` fehlt, Standard): `{ "available": false }`.
- **Eingeschaltet:** `{ "available": true, "place": "Westerburg", "current": {…} | null, "min24h": number | null, "max24h": number | null, "series": [{ "t": ISO, "temperature": number }] }`. `current` (null, solange keine Messung vorliegt) enthält `measuredAt` (Zeitpunkt der Messung der Station), `stale` (Messung älter als 1 Stunde) und, soweit die Station sie liefert, `temperature` (°C), `humidity` (%), `pressure` (hPa), `rain1h`/`rain24h` (mm), `windKmh`, `gustKmh`, `windAngle` (Grad; sonst `null`). `min24h`/`max24h`/`series` (je 15 Minuten die letzte Messung der letzten 24 Stunden, aufsteigend) kommen aus der eigenen Zwischenspeicherung (`weather_samples`, 7 Tage).
- **Nie enthalten:** Straße, Koordinaten, Höhe, Karte, Stations-ID (MAC), Zugangsdaten. Der Ortsname ist die Einstellung `WEATHER_PLACE`.
- **Abruf (Server):** `server/src/weather/service.ts`, im eigenen Prozess `lx-fampad-weather.service` (`cli/weather-poller.ts`); die API-Route liest nur aus der Datenbank. `GET https://api.netatmo.com/api/getpublicdata` mit Suchrechteck (`WEATHER_BBOX`) und Filter der Antwort auf die MAC (`WEATHER_STATION_MAC`); kein Weathermap-Scraping. Alle 10 Minuten (`WEATHER_POLL_MS`, in Produktion mindestens 5 Minuten), bei Fehlern mit Backoff (verdoppelnd bis 2 Stunden), ein Takt je Prozess. OAuth2 mit Refresh-Token und **Rotation**: das neue Token wird unter Zeilensperre (`FOR UPDATE`) in derselben Transaktion gespeichert, in der es abgeholt wird; `invalid_grant` schaltet den Abruf ab (`weather_credentials.disabled_at`) bis zur neuen Eingabe. Client-ID, Client-Secret und Refresh-Token stehen nur AES-256-GCM-verschlüsselt (Schlüssel per HKDF aus `AUTH_SECRET_KEY`, Zweck `weather`) in der Datenbank; eingegeben werden sie nur per Kommandozeile (`npm run weather-setup`, ohne Echo), nie über die API. Antworten von Netatmo werden nur als Zahlen in plausiblen Bereichen übernommen und nie ins Log geschrieben.

## Push (UnifiedPush, nur Android)

Push ist ein **Wecker ohne Inhalt**: kein Text, kein Titel, keine Tags, keine Namen. Das Gerät gleicht danach per `POST /sync` ab und zeigt selbst eine lokale Benachrichtigung. Der Server veröffentlicht auf dem eigenen ntfy (`NTFY_URL`, Loopback) mit dem Token `NTFY_TOKEN`; fehlt eines von beiden, ist Push still aus (ein Hinweis im Log, kein Fehler, `GET /me/push` meldet `available: false`).

- **Endpunkt melden (`PUT /me/push`)**: Das Gerät gehört immer zur Sitzung (nie eine ID im Body, der Body ist strikt). Akzeptiert wird nur ein Endpunkt der Form `https://<NTFY_PUBLIC_HOST>/up<12–64 Zeichen [A-Za-z0-9_-]>`, optional mit `?up=1` (so meldet ihn die ntfy-App: Präfix `up` plus 12 Zeichen); kein Port, keine Zugangsdaten, kein Fragment, keine Prozent-Kodierung, kein weiterer Pfad, keine IP. Geprüft wird auf dem Rohtext (kein URL-Parser). Gespeichert wird nur das Topic (`push_endpoints`, je Gerät eine Zeile). **Gepostet wird nie an die gemeldete URL**, sondern an `NTFY_URL` + Topic (SSRF-Schutz). Ein Topic gehört einem Gerät (bei fremdem Topic dieselbe Antwort `400 invalid_endpoint` wie bei ungültigem; die App meldet dann einmal ab und registriert neu, damit der Verteiler ein neues Topic vergibt); eine Neuanmeldung ersetzt den alten Endpunkt (Rotation) und aktiviert einen deaktivierten wieder. Strikt rate-limitiert wie die Anmeldung.
- **Auslöser**: Steigt die Revision der Familie durch eine Änderung im Sync, bekommen die Geräte einen Wecker, deren Person (1) aktiv ist und deren Rolle die Änderung sehen darf (dieselbe Rollen-Sicht wie beim WebSocket-Hinweis `rev`), (2) nicht das Gerät ist, das die Änderung ausgelöst hat (die anderen Geräte derselben Person werden geweckt und gleichen ab; ob danach eine Anzeige erscheint, entscheidet der `EreignisBenachrichtiger` der App, eigene Änderungen zeigt er nicht an), (3) keine lebendige WebSocket-Verbindung hat (Lebenszeichen, also Pong oder Nachricht, innerhalb von 1,5 Ping-Intervallen; ein wegen offener Verbindung nicht gesendeter Wecker wird nach Ablauf der Ping-Frist einmal nachgeprüft und dann gesendet, wenn die Verbindung nicht mehr lebendig ist), (4) vom Empfängerfilter zugelassen ist (siehe unten). Das Entfernen eines Mitglieds (Bereinigen von Verweisen) löst keinen Push aus.
- **Entprellung je Gerät**: höchstens ein Wecker je 10 s; was dazwischen anfällt, wird zu genau einem weiteren zusammengefasst. ntfy-`429` (mit `Retry-After`, höchstens 10 min) pausiert den Versand und fasst zusammen, ohne den Endpunkt zu bestrafen. `401/403` von ntfy (Token oder Rechte falsch) pausiert 5 min und lässt die Endpunkte unberührt (Betriebsfehler, im Log). Kein Wiederholen bei 4xx.
- **Netz-/5xx-Fehler** (Zeitlimit 5 s eingeschlossen) sind Störungen des ntfy, nicht des Geräts: globale Pause von 30 s, kein Zählen je Endpunkt (ein ntfy-Neustart deaktiviert keine Endpunkte), kein Wiederholen. Nach `429` und `401/403` wird je Gerät genau ein zusammengefasster Wecker nach der Pause neu geplant; ein Timer prüft die Pause beim Ablauf neu (wurde sie verlängert, wartet er die Restdauer).
- **Deaktivierung**: ntfy-`404/410` deaktiviert den Endpunkt sofort, 5 aufeinanderfolgende gezielte 4xx-Antworten (z. B. 400) ebenso; ein Erfolg setzt den Zähler zurück. Wieder aktiv durch erneutes `PUT /me/push`.
- **Löschen**: Abmelden (`/auth/logout`, `logout-all`, Gerät entfernen, Mitglied entfernen, Widerruf) löscht den Endpunkt; zusätzlich Fremdschlüssel `ON DELETE CASCADE` auf dem Gerät.
- **Empfängerfilter (Erweiterungsstelle für Chat)**: `app.push.addRecipientFilter(async (ev) => userIds | null)` (`server/src/push/service.ts`). `ev` trägt `familyId`, `rev`, `roles` (Rollen-Sicht) und `origin`. Der Chat liefert damit die Teilnehmer (Privatchats: nur diese); mehrere Filter wirken als Schnitt, `null` heißt keine Einschränkung. Ohne Filter gilt allein die Rollen-Sicht.
- **Test-Wecker** (`POST /me/push/test`) respektiert die globale Pause und hat ein eigenes Limit je Gerät. In der App heißt „angekommen“ nur, dass etwas ankam (es ist kein Herkunftsnachweis).
- **App**: `unifiedpush` initialisiert bei jedem Start (auch beim Hintergrund-Start durch das Plugin, `main(["--unifiedpush-bg"])`: nur abgleichen, keine Oberfläche); bei jedem Start erneut `register`; Hintergrund-Läufe dürfen **nie** das Refresh-Token einlösen (ApiClient `refreshErlaubt: false`: ist das Access-Token abgelaufen, endet der Lauf ohne Tokenzugriff, der nächste Start der App gleicht ab), laufen einzeln (Single-Flight) und höchstens alle 10 s (Wecker dazwischen werden zu einem Lauf), mit Höchstdauer 25 s; `onNewEndpoint` -> `PUT /me/push`; `onMessage` (Inhalt wird verworfen) -> Abgleich, danach die Schnittstelle `EreignisBenachrichtiger.neueEreignisse(rev, vorher)` (`app/lib/data/push/push_wecker.dart`) für lokale Benachrichtigungen (der Erinnerungs-Zweig hängt dort seine Umsetzung ein).

## WebSocket `/ws`

1. `POST /ws-ticket` (angemeldet) → `{ ticket }`.
2. `wss://familie.lx-labs.dev/ws` öffnen (kein Ticket in der URL!); der Server sendet `{type:"hello", protocolVersion, serverVersion}`.
3. Als **erste Nachricht** `{ "type": "auth", "ticket": "<ticket>" }` senden (innerhalb von 5 s). Antwort `{type:"ready"}`; bei ungültigem, abgelaufenem oder schon benutztem Ticket schließt der Server mit Code `4401` und zählt den Fehlversuch gegen die IP.
   Danach meldet der Server nach **jedem Commit einer Änderung** im Sync den Sockets der Familie, **deren Rolle die Änderung sehen darf**, `{ "type": "rev", "rev": N }` (ohne Inhalt; auch an das Gerät, das die Änderung gesendet hat). Wer einen Datensatz nicht sehen darf, erfährt nicht einmal, dass es eine Änderung gab; entzieht eine Änderung die Sicht (Freigabe zurückgenommen), erfahren es die Rollen vorher und nachher. Das Bereinigen von Verweisen beim Entfernen eines Mitglieds geht an alle Rollen. Änderungen an **Privatchats** (Direkt- und Gruppenchats) gehen nur an deren Teilnehmer (nach Person, nicht nach Rolle). Der Client gleicht daraufhin ab (`POST /sync`), wenn `N` größer als sein Stand ist. Der Client kann `{ "type": "ping" }` senden und bekommt `{ "type": "pong" }` (die App tut das alle 25 s und verbindet neu, wenn das Pong ausbleibt).
4. Browser mit gültigem Session-Cookie sind schon beim Upgrade angemeldet.
5. Limits: Nachrichten je Socket (30 je 10 s, sonst Code `4429`), Verbindungen je IP (IPv6: je /64; 10, vor dem Upgrade `429`) und je Person (8, Code `4429`).
6. **Widerruf:** Abmelden, Gerät entfernen, „überall abmelden“, Rollenwechsel und Entfernen schließen die betroffenen Sockets sofort mit Code `4401`. Zusätzlich prüft der Server bei jedem Ping (30 s), ob Sitzung und Mitgliedschaft noch gelten (sonst `4401`), und hält die Rolle der Verbindung aktuell.
7. **Mitglieder geändert:** ändern sich die Mitglieder der Familie (Person tritt per Einladung bei oder wird zurückgesetzt, Freigabe, Ablehnen, Entfernen, Rolle, Familienrolle, Name, Farbe, Profilbild, Schlüssel angelegt oder gewechselt), sendet der Server nach dem Commit `{ "type": "members_changed" }` an alle Sockets **der eigenen Familie** (nie familienübergreifend, nicht an Standort-Verbindungen, ohne jeden Inhalt). Die App lädt daraufhin `GET /members` neu (höchstens alle 5 s, zu frühe Hinweise werden gebündelt nachgeholt). Clients ignorieren unbekannte Nachrichtentypen (ältere Apps tun das und bleiben unberührt).
8. **Standort teilen:** zusätzliche Nachrichten `loc_*`, siehe Abschnitt „Standort“ unten.

## Standort (WebSocket `loc_*`, flüchtig)

Standort teilen läuft **nur über den WebSocket** und **nur im Prozessspeicher** des Servers: keine Tabelle, keine Migration, kein Backup, keine Historie, nichts im Log (nicht einmal Kennungen von Freigaben). Der Server reicht opake Pakete weiter; Wrap und Paket sind für ihn Base64url-Zeichenketten, geprüft werden nur Form (`^[A-Za-z0-9_-]+$`) und Länge. Aufbau und Verfahren: `docs/PROJEKTBESCHREIBUNG.md`, Abschnitt 6f. Alle `loc_*`-Nachrichten brauchen eine angemeldete Verbindung (vorher `error` `unauthenticated`) und zählen für das Nachrichtenlimit je Socket. `loc_start`, `loc_pos`, `loc_extend` und `loc_stop` werden je Socket der Reihe nach verarbeitet.

**Client → Server**

| Nachricht | Inhalt und Regeln |
| --- | --- |
| `loc_start` | `{ shareId (UUID, vom Client), endsAt (Epoch-ms, in der Zukunft, höchstens `LOC_MAX_DURATION_MS` = 12 h ab jetzt), recipients: [{ userId, wrap }] }`. 1 bis 30 Empfänger, jede ID einmal, **nur aktive Mitglieder der Familie der Sitzung, nie die Person selbst** (Regel `locationRecipients` in `sync/permissions.ts`; Mitglieder kommen aus der Datenbank). Eine neue Freigabe **ersetzt** die alte derselben Person (die alte endet mit `replaced`). Antwort `loc_started`. |
| `loc_pos` | `{ shareId, packet }`, Paket ≤ 1024 Zeichen. Nur vom **Gerät, das gestartet hat** (gleiche Person und Gerät). Mindestabstand je Freigabe `LOC_MIN_INTERVAL_MS` (1000), sonst `loc_error` `rate_limited` (das Paket wird verworfen, nichts endet). |
| `loc_extend` | `{ shareId, endsAt }`, gleiche Grenzen wie beim Start. Antwort `loc_active`. |
| `loc_hello` | `{}`. Die Verbindung gehört dem Standort-Kanal der App: der Server zählt sie weder als „Gerät ist live“ (Push) noch schickt er ihr `rev`-Hinweise. |
| `loc_stop` | `{ shareId }`. Beendet; Empfänger bekommen `loc_stop` mit `reason: "stopped"`. |

**Server → Client**

| Nachricht | Inhalt |
| --- | --- |
| `loc_started` / `loc_active` | `{ shareId, endsAt }` an den Sender: bestätigt Start bzw. Verlängern; `loc_active` kommt außerdem, wenn sich das Sendergerät innerhalb der Schonfrist wieder verbindet. |
| `loc_start` | `{ from, shareId, endsAt, wrap }` an **jeden Empfänger einzeln, nur mit dessen eigenem Wrap** (Empfänger ohne offene Verbindung weckt der Server zusätzlich per Push-Wecker ohne Inhalt, je Sender und Empfänger höchstens alle 10 Minuten, nie bei Verlängern, Wiederverbinden oder Beenden; die App holt `loc_start` dann bei einer Kurzverbindung ab und meldet es lokal); ein später verbundener Empfänger bekommt es beim Anmelden nachgereicht, danach die letzte Position als `loc_pos`. |
| `loc_extend` | `{ from, shareId, endsAt }` an die Empfänger, wenn der Sender verlängert. |
| `loc_pos` | `{ from, shareId, packet }` an die Empfänger der Freigabe (nie an den Sender, nie an Unbeteiligte oder andere Familien). |
| `loc_stop` | `{ from, shareId, reason }` an Empfänger und Sender; `reason`: `stopped`, `expired`, `disconnected`, `removed`, `replaced`. |
| `loc_error` | `{ code, shareId? }`: `bad_request`, `bad_duration`, `bad_recipients`, `share_exists`, `rate_limited`, `too_many_shares`, `forbidden`, `unknown_share` (auch für fremde Freigaben und Sendungen vom falschen Gerät), `unavailable` (u. a. wenn die Mitgliederprüfung länger als `LOC_DIRECTORY_TIMEOUT_MS` (5 s) braucht; die Nachrichten des Sockets laufen danach weiter). |

**Auto-Ende:** Ablauf (`endsAt`), `loc_stop`, Widerruf (Abmelden, Gerät oder Mitglied entfernen, Rollenwechsel: sofort), **Sendergerät länger als `LOC_GRACE_MS` (90 s) ohne Verbindung**, Sender nicht mehr aktives Mitglied. Entfernte Empfänger werden bei der regelmäßigen Prüfung (Abstand 12 × `LOC_SWEEP_MS`) aus der Freigabe genommen; hängt die Datenbank dabei (länger als `LOC_DIRECTORY_TIMEOUT_MS`, Standard 5 s), bleibt die Freigabe unverändert, Ablauf (`endsAt`) und Schonfrist gelten weiter, der nächste Lauf versucht es erneut. **Limits:** 10 Starts je Person in 10 Minuten, `LOC_MAX_PER_MINUTE` (40) Positionen je Freigabe und Minute (Gleitfenster; die App sendet höchstens alle 3 s, also 20 je Minute; darüber `loc_error` `rate_limited`), Mindestabstand `LOC_MIN_INTERVAL_MS` (1 s), `LOC_MAX_SHARES_PER_FAMILY` (50) Freigaben je Familie, Wrap ≤ 1024 und Paket ≤ 1024 Zeichen. Einstellungen: `server/.env.example`.
