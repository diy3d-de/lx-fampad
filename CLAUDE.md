# lx-fampad

Selbst gehostete Familien-Zentrale (Kalender, Chat, Listen, Aufgaben, Dateien, später Fotos, Karte u. a.) für die eigene Familie.
Web und Android aus einer Flutter-Codebasis, Server auf dem netcup-VPS von lx-labs.dev. Domain: **familie.lx-labs.dev**.
Sprache aller Inhalte, UI-Texte und Commit-Nachrichten: **Deutsch**, Ansprache per **du**. Verbindliche Beschreibung: `docs/PROJEKTBESCHREIBUNG.md`, Versionen: `docs/VERSIONEN.md`, Mockups: `docs/mockups/`.

E2EE (Chat-Verschlüsselung): **Phase 1 (Schlüsselverwaltung) und Phase 2 (verschlüsselter Chat: Epochenschlüssel, signierte Wraps, Rotation, Hülle `e1`) gebaut** (v0.3.0); Beschreibung `docs/PROJEKTBESCHREIBUNG.md`, Abschnitt 9a.

Stand: **v0.3.0 „Chat-Paket“** (Server: Konten und Anmeldung seit 1a, Sync-Kern; App: Anmeldung, Einladungen, Konto, Admin seit 1b, Sync und **Listen** in 1c-1, **Kalender-Kern** (Termine, Teilnehmer, Ausnahmen, Serien) in 1c-2a, **Aufgaben** (mit Unteraufgaben und einfacher Wiederholung; Abschnitt 6e) in 1c-4a, **Chat** (Familienchat, Direktchats, Gruppen, Lesestand; Abschnitt 6c) **Ende-zu-Ende verschlüsselt** (9a), **Push** (UnifiedPush-Wecker, lokale Benachrichtigung „Neue Nachricht in <Chat>“ ohne Inhalt; 6d); Dateien folgen als eigene Teile auf demselben Kern). Fahrplan in `docs/PROJEKTBESCHREIBUNG.md`, Abschnitt 12; Endpunkte in `docs/API.md`.

## Stack

- **Server** (`server/`): Node 24.21.0, TypeScript 6.0.3, Fastify 5.12.5, `@fastify/websocket` 11.3.3, Drizzle ORM 0.45.3 (+ drizzle-kit 0.31.11), PostgreSQL 17, Vitest 5.0.3, ESLint. Anmeldung: `@simplewebauthn/server` 14.0.3 (Passkeys), `argon2` 0.45.1 (Argon2id), `otplib` 13.5.0 (TOTP), `zod` 4.6.5 (Eingabevalidierung). Konfiguration nur über Umgebungsvariablen (`server/.env.example`); ohne `NODE_ENV` gilt `production` (fail-closed), unbekannte Werte brechen den Start ab, lokal `NODE_ENV=development` in `.env`. In `production` ist `AUTH_SECRET_KEY` Pflicht (Hauptschlüssel für TOTP-Verschlüsselung und HMACs, nie in der Datenbank, nie ändern).
- **App** (`app/`): Flutter 3.47.6 / Dart 3.13.5 (Android + Web, kein iOS), Riverpod 3.4.3, drift 2.35.1 (SQLite, im Web WASM/OPFS), `rrule` 0.2.18 + `timezone` 0.11.1 (Terminserien; Zeitzonen-Daten als Asset `assets/tz/latest.tzf`); Anmeldung: `flutter_secure_storage` 11.2.0, `passkeys` 2.23.1 (Web: selbst gehostetes `web/passkeys-bundle.js`), `mobile_scanner` 7.4.2 (QR-Scan, nur Android), `qr_flutter` 4.1.0; E2EE: `sodium` 4.1.1+2 (libsodium; Android per Build-Hook mit C-Compiler/NDK, Web: selbst gehostetes `web/sodium.js` Sumo, Prüfsumme in `web-assets.sha256`; kein CDN). Web ohne CDN: `--no-web-resources-cdn`, Schriften gebündelt, `fontFallbackBaseUrl` auf die eigene Domain. `analyzer` (14.4.0) und `sqlite3` (3.7.0, passend zu `web/sqlite3.wasm`) sind bewusst gepinnt; `app/web-assets.sha256` hält die Prüfsummen der Web-Binärdateien (inkl. `passkeys-bundle.js`).
- **Deploy** (`deploy/`): Caddy (Site `familie.lx-labs.dev`, ntfy auf `ntfy.familie.lx-labs.dev`), systemd-Dienst `lx-fampad`, `deploy.sh`, `deploy-web.sh`. Einrichtung: `deploy/README.md`.
- **Versionen sind exakt gepinnt** (kein `^`, kein `~`), Lockfiles (`package-lock.json`, `pubspec.lock`) werden eingecheckt. Neue Pakete nur mit Version, die mindestens 14 Tage alt ist (auch transitiv, sonst per `dependency_overrides` festhalten); in `docs/VERSIONEN.md` eintragen.

## Befehle

```bash
# Server (in server/)
npm ci
npm run dev          # tsx watch, liest .env
npm run lint         # ESLint
npm run typecheck    # tsc --noEmit
npm test             # Vitest (Schema-, Anmelde- und Sync-Tests laufen gegen PGlite; mit TEST_DATABASE_URL=postgres://… zusätzlich gegen echtes PostgreSQL 17, dort auch die Parallelitäts-Tests)
npm run build        # nach dist/
npm run db:generate  # neue Migration aus src/db/schema.ts erzeugen (drizzle/)
npm run migrate      # Migrationen anwenden (MIGRATION_DATABASE_URL, sonst DATABASE_URL; nach build)
npm run bootstrap    # Erstinstallation: Familie + Einladungslink für den ersten Admin (nach build); --reset <E-Mail> für den Notfall; auf dem Server: sudo node --env-file=/etc/lx-fampad/env /srv/fampad/server/dist/cli/bootstrap.js

# App (in app/)
flutter pub get --enforce-lockfile   # pubspec.lock ist eingecheckt; neu auflösen nur bewusst mit "flutter pub get"
dart run build_runner build --delete-conflicting-outputs   # drift: erzeugt lib/data/app_database.g.dart (nicht eingecheckt); in der CI ohne die Option
flutter analyze
flutter test        # libsodium-Tests brauchen die native Bibliothek (Build-Hook = C-Compiler): ohne sie (z. B. Windows ohne Visual Studio, dann NIX_SKIP_SODIUM_BUILD_HOOKS=1) werden sie übersprungen; in der CI ist SODIUM_ERFORDERLICH=1 gesetzt (dann Pflicht)
flutter run -d chrome
flutter build web --release --no-web-resources-cdn
# Vertragsprüfung gegen den echten Server (nicht Teil von flutter test): app/tool/vertrag_test.dart (Anmeldung und seit 1c der Sync mit zwei Geräten, Konflikten, Rechten, WebSocket, mehrseitigem Snapshot bei purged_rev > 0, Geisterliste), Ablauf im Dateikopf (enthält die Ende-zu-Ende-Prüfung des Chats mit drei Personen und zwei Geräten)

# Werkzeuge (Repo-Wurzel)
node --test "tools/*.test.mjs"                                      # Test der Manifest-Signatur
node tools/update-manifest.mjs keygen|sign …            # Update-Schlüssel, Manifest signieren (tools/README.md)

# Deploy
ssh lx-labs bash lx-fampad/deploy/deploy.sh   # Server
deploy/deploy-web.sh                                    # Web-App
```

## Design-Regeln (verbindlich)

Vorbild ist **lx-urlaubsplanung** (`src/app/globals.css`, `mobile/lib/main.dart`); Tokens stehen in `docs/PROJEKTBESCHREIBUNG.md` (Abschnitt Design) und in `app/lib/constants.dart`.

- **Nur Dark Mode.** Hintergrund `#090A0F` mit violett-cyanem Schimmer oben (`LxBackground`), kein Punktraster. Für Drucklisten später heller Druckstil.
- **Farben nur über Konstanten** (auch Weiß: `kTextStrong`, kein `Colors.white`) (`kBg`, `kSurface`, `kAccent`, …) in `constants.dart`; keine Hex-Werte in Widgets. Neue Farben dort anlegen und in der Projektbeschreibung ergänzen.
- **Akzent** Cyber Cyan `#00F0FF` (Buttons, Auswahl), `neural` `#7C3AED` für Glow/Sonderfälle, `terminal` `#10B981` für „online/synchron“, `danger` `#FF5F57`.
- **Personenfarben:** feste Palette von 10 Farben (`personPalette`), je Familienmitglied einheitlich in Kalender, Chat, Karte, Listen.
- **Schrift:** Inter (Überschriften fett `w800`, Letter-Spacing negativ), JetBrains Mono für Kennzahlen, Status, Uhrzeiten, Metadaten und Abschnitts-Labels (`// zuletzt`, `MonoLabel`). Selbst gehostet, nie Google-Fonts-Abruf.
- **Material 3:** transparenter Scaffold über dem Verlauf, `NavigationBar` in `surface` mit Akzent-Indikator und Mono-Beschriftung, `FilledButton` in Cyan, Dialoge/Bottom-Sheets in `surface`, Karten mit 1-px-Rand `border` (`LxCard`). Keine weichen Drop-Shadows.
- Touch-Ziele mindestens 44 px (feste Höhen per `mainAxisExtent`, nie `childAspectRatio`), Inhalt auf `kMaxContentWidth` (720 px) begrenzt, Layout ab 360 px Breite auch bei Textskalierung 1.5, Beschriftungen für Screenreader (`Semantics`/`tooltip`).
- Muster aus lx-urlaubsplanung (Sync-Indikator, Update-Dialog, Einstellungen) übernehmen statt neu erfinden.
- **Kopfzeile aller Tabs identisch:** Jeder Tab beginnt mit `TabKopfzeile(title: …)` (`lib/widgets/kopfzeile.dart`: Datum als `MonoLabel`, Titel, Sync-Indikator, Profil-Knopf; im Desktop-Layout ab `kDesktopBreakpoint` nur Datum und Titel, weil Fußzeile und Seitenleiste Sync und Profil zeigen); nur der Titel ist tab-spezifisch, keine eigenen Aktionen oder Status-Pillen in der Kopfzeile. Der Profil-Knopf zeigt Initialen in der Personenfarbe und nimmt später das Benutzerbild (`bild`) auf.

## Konventionen

- Server: ESM, strikt typisiert, keine Fachlogik in Routen-Dateien, die Fastify-App entsteht in `buildApp()` (testbar mit `app.inject`). Jede fachliche Tabelle hat `family_id`; Sync-Tabellen haben `rev`, `field_revs`, `deleted_at` (Tombstone). Migrationen nur vorwärts und rückwärtskompatibel zur Vorgängerversion der App.
- **Familienrolle** (`memberships.family_role`, feste Liste `FAMILY_ROLES`/`FamilyRole`, CHECK in der Datenbank) ist **reine Anzeige**: nie in Rechte, Sichtbarkeit, Sync, Chat, Push oder Kalender einrechnen, Rechte hängen nur an `role`. Setzen: `PUT /me/family-role` (jede Person für sich) und `PUT /members/:id/family-role` (nur Admin); App zeigt sie über `rollenPillen()` (`features/auth/auth_widgets.dart`) als neutrale Pille.
- **Rollen:** nur `admin`, `parent`, `child` (keine Gäste; Zugriff nur für eingeladene Familienmitglieder). Freigabe-Stufen nur `parents` und `family`; die Eingabe `all` alter Apps (bis 0.2.0) nimmt der Server weiter an und speichert `family` (`AUDIENCE_INPUT` in `sync/entities/common.ts`); die App behandelt unbekannte Rollen als `child` und unbekannte Stufen als `family`. Migration 0005 hat die Gast-Konten entfernt.
- Fremdschlüssel zwischen familiengebundenen Tabellen sind zusammengesetzt `(family_id, id)`; Ziel-Tabellen brauchen dafür `unique(...)` (kein `uniqueIndex`, drizzle-kit legt Fremdschlüssel vor den Indizes an). Schema-Änderungen: `src/db/schema.ts` ändern, `npm run db:generate`, erzeugte Dateien in `drizzle/` einchecken. Nie eine eingecheckte Migration nachträglich ändern.
- App: ein Bereich = ein Ordner unter `lib/features/`; Zustand mit Riverpod; keine Netzwerk- oder dart:io-Zugriffe in Code, der im Web läuft, ohne bedingten Import (siehe `features/update/apk_downloader*.dart`).
- Anmeldung (Server): Geheimnisse nur gehasht oder verschlüsselt (Tokens/Tickets SHA-256, Passwörter Argon2id, Codes/PINs HMAC, TOTP AES-256-GCM); Einmal-Einlösungen immer atomar (`UPDATE/DELETE … RETURNING`, Zählen vor dem Vergleich); alle Fehlschläge der Anmeldung antworten gleich; jede Route, die Familiendaten liefert, filtert über die Familie der Sitzung (fremde Objekte = 404); neue Prüfungen für sensible Aktionen über `requireStepUp`. Datenbank-Rollen: Laufzeit nur DML (`DATABASE_URL`), Migrationen mit `MIGRATION_DATABASE_URL`.
- Offline-first: UI schreibt in die lokale DB/Outbox und wartet nie auf den Server (Sync-Protokoll: Projektbeschreibung Abschnitt 6 und 6a, `docs/API.md`, Abschnitt „Sync“).
- Kalender: Familienzeitzone fest Europe/Berlin; Zeittermine als UTC + `tzid`, ganztägige als Tage (Ende exklusiv); Serien rechnet nur der Client (`rrule` auf Wanduhrzeit der `tzid` als UTC getarnt, danach `timezone`), der Server prüft nur die Form (`sync/rrule.ts`); Ausnahmen mit fester ID aus Termin und Beginn; nie eine Serie über `any`-Zeiten oder Geräte-Zeitzone rechnen. Serien teilen, kürzen und Ausnahmen vergleichen immer gegen den **ursprünglichen** Beginn (`Vorkommen.original*`), Ausnahmen nie löschen (nur zurücksetzen), `AuswahlKnopf` nie mit `Container(alignment:)` füllen (stapelt sich im `Wrap`).
- Neue Sync-Entität (Aufgaben, Chat, Dateien): Tabelle mit `syncColumns()` und `family_id` (Migration), Eintrag im **Register des Servers** (`server/src/sync/entities/*.ts` + `index.ts`: Felder mit Zod-Prüfung, Rechte-Regel je Rolle, Elternbeziehung, `userRefs`, Obergrenzen, optional `check` für Regeln über mehrere Felder) und im **Register der App** (`app/lib/data/sync/sync_entities.dart` + drift-Tabelle + Repository); Protokoll und Rechte-Modell bleiben unverändert. Rechte nie in Routen oder Engine, nur in der Regeltabelle (`sync/permissions.ts`; `assignedFields` für zuständige Personen, `derive` im Register für vom Server gesetzte Werte wie `erledigtVon`); nicht lesbare Datensätze ergeben `not_found`. Jede Op wird feldweise geprüft (kein `any`, keine Inhalte im Log); Verweise auf Mitglieder (`ON DELETE SET NULL`) prüft die Engine und bereinigt `sync/refs.ts`. Weitere Register-Haken: `guard` (zusätzliche Sperre je Aktion), `onUpdate` (vom Server gesetzte Felder), `rate` (Neuanlagen je Person und Minute), `memberArray` (Teilnehmerliste mit Mitglieds-IDs, `refs.ts` nimmt die Person heraus) und `lostSight` (nur wer die Sicht verliert, bekommt `hidden`). **Jede drift-Migration, die Tabellen für neue Sync-Entitäten anlegt, MUSS den Sync-Fortschritt zurücksetzen** (`sync_meta`-Schlüssel `sinceRev` und `snapshotRev` löschen, nicht deviceId/ownerUserId/members/Outbox), sonst kommen ältere Datensätze der Entität nie an (siehe `onUpgrade` in `app_database.dart`, Projektbeschreibung 6a).
- Sync (App): lokale Änderungen nur über `SyncStore.aendern/loeschen` (Tabelle + Ausgang in einer Transaktion), Serverantworten nur über `SyncStore.uebernehmen`; ein Abgleich läuft immer nur einzeln (`SyncController`), 401 nie in der Sync-Schleife wiederholen, vor dem Leeren der Datenbank den Sync anhalten (`lokaleDatenWiper`).
- Widget-Tests mit drift: Datenbank mit `DatabaseConnection(NativeDatabase.memory(), closeStreamsSynchronously: true)` anlegen (sonst bleiben Timer von drift stehen), Hilfen in `test/support/test_app.dart`.
- App-Anmeldung: Token nie loggen oder in localStorage legen; Refresh nie parallel oder blind wiederholen (Familien-Widerruf); Einladungs-Token nur im Fragment/POST-Body; Screens mit Geheimnissen in `BildschirmSchutz` (FLAG_SECURE); Zwischenablage nur auf Klick; Meldungen nur aus `ApiException`/`PasskeyException` (keine Servertexte).
- Chat: Direkt- und Gruppenchats sieht NUR ihre Teilnehmer (`Facts.participants` in `sync/permissions.ts`: harte Grenze vor jeder Rollenregel, nie ein Rollen-Durchgriff für Admin/Eltern; der WebSocket-Hinweis geht nach Person, `usersThatMayRead`). Nachrichtentext und Gruppenname sind für den Server **undurchsichtig** (nur Länge/Zeichensatz prüfen, nie auswerten, loggen, indizieren oder in Push zeigen); die App liest und schreibt sie ausschließlich über `NachrichtenInhalt` (heute `p1:`, später `e1:`). Admins löschen fremde Nachrichten nur im Familienchat. Feste IDs (Familienchat, Direktchat, Lesestand) erzwingt der Server per `idValid` (abgeleitet wie in der App, Known-Answer-Tests auf beiden Seiten), Gruppen brauchen eine UUID v4; Chat-Zeiten stehen in der App als Millisekunden (`MsDatumConverter`).
- E2EE: nur geprüfte libsodium-Bausteine über `CryptoProvider`, **keine eigenen Primitive, kein eigener Ratchet**. Der Server speichert nie ein Geheimnis (nur öffentliche Schlüssel und undurchsichtige Blobs), Schlüsselmaterial und Klartext nie in Log, Audit oder Fehlermeldungen. Der geheime Personenschlüssel liegt nur im Schlüsselspeicher des Geräts (Android Keystore bzw. Web: AES-GCM mit nicht exportierbarem WebCrypto-Schlüssel in IndexedDB) und verlässt es nur verschlüsselt (Sicherung mit Wiederherstellungsschlüssel, Übertragung per QR); Anzeige von Wiederherstellungsschlüssel und Übertragungscode nur in `BildschirmSchutz`, Zwischenablage nur auf Klick. Neue verschlüsselte Inhalte immer in der versionierten Hülle (`huelle.dart`: AAD, `sender_key_version`, Signatur mit Domänenpräfix und Längenrahmen aus `domaenen.dart`; neue Signaturarten brauchen ein eigenes Präfix). Der Wiper für Abmelden läuft über `wiperVerkettet` (Schlüssel wird unabhängig vom Datenbank-Wipe gelöscht). Android-Build und `flutter test` brauchen wegen des libsodium-Hooks NDK bzw. einen C-Compiler (CI hat sie), lokal unter Windows `NIX_SKIP_SODIUM_BUILD_HOOKS=1`. Schlüsselwechsel einer Person warnt (TOFU, `vertrauen.dart`), nie stillschweigend übernehmen. CSP nicht lockern (`wasm-unsafe-eval` steht schon für CanvasKit/sqlite3). **Chat-Verschlüsselung (Phase 2):** Epochenschlüssel nie auf Platte oder Server, nur im Arbeitsspeicher (Wraps der eigenen Person öffnen); verteilt wird nur an Schlüssel, denen das Gerät vertraut (gemerkt UND gleich dem Server), der Verteiler-Schlüssel kommt aus dem TOFU-Speicher (nie vom Server, für die eigene Person der eigene); eine ungeprüfte Schlüsseländerung löst **keine** Rotation aus. Nachrichten nur über `NachrichtenInhalt` (`e1:`; `p1:` in einem `e1`-Chat nie anzeigen; `l1:` nur für Nachrichten, die der Ausgang kennt), der Ausgang hält Klartext (`l1:`) und `SyncStore.naechsteOps` lässt ihn nie hinaus: Verschlüsselt wird erst beim Senden mit der höchsten **bestätigten** Epoche, für die das Gerät den Schlüssel hat (sonst warten). Jede Änderung der Teilnehmer legt in derselben Transaktion eine neue Epoche an (`teilnehmerAendern`), Rotation und Wraps nie ohne `SyncStore.aendernMehrere`. Der Server wertet Wraps, Listen und Chiffretext nie aus (nur Form, Größe, Eindeutigkeit, Sicht); feste IDs der Epochen und Wraps (`chat-ids.ts`/`chat_ids.dart`). Die Oberfläche zeigt beim Anlegen und Hinzufügen immer Mitglieder und Sicherheitscode (`mitgliederBestaetigen`). Gruppenname ist `p1:`-Metadatum, nie Nachrichteninhalt dort ablegen.
- Erinnerungen: Termine und Aufgaben (`erinnerungMin`, Abschnitt 6e) teilen sich Dienst, Fenster (300) und Planung (`planeErinnerungen(aufgaben: …)`); Aufgaben nur für Zuständige (ohne Zuständige: Ersteller), Payload `aufgabe|<UUID>`, Schalter „Aufgaben-Erinnerungen“ (lokal, Standard an). Kein Schema-/Serverbezug, nie Inhalt über Push.
- Datenschutz: keine Tracker, keine Fremd-Einbindungen (Schriften, Karten, Skripte), Push ohne Inhalte, Standort nur durch die Person selbst. CSP in `deploy/Caddyfile` nicht lockern, ohne Security zu fragen.
- Push: nie Inhalt im Wecker (kein Titel, keine Tags); gemeldete Endpunkte nur über `push/endpoint.ts` annehmen und nie dorthin senden, sondern an `NTFY_URL`; kein eingebetteter FCM-Verteiler (Google). Teilnehmer-Filter (Chat) über `PushService.addRecipientFilter`, lokale Benachrichtigungen über `EreignisBenachrichtiger`. Die lokale Chat-Benachrichtigung (`ChatBenachrichtiger`) zeigt nie einen Nachrichteninhalt, nur „Neue Nachricht in <Chat>“; auf dem Sperrbildschirm privat, außer die Einstellung der Erinnerungen („Titel zeigen“) ist an. Der Push-Empfänger eines Chats ergibt sich aus der Sync-Regeltabelle (`users` im Ereignis: nur Teilnehmer privater Chats), nie aus Rollen allein.
- `applicationId` (`dev.lx_labs.fampad`) und Android-Signaturschlüssel nie ändern.
- Geheimnisse (`.env`, `key.properties`, Keystores, Signaturschlüssel des Update-Manifests) nie einchecken. `kUpdatePublicKey` ist bis zum ersten Release ein Platzhalter (siehe `tools/README.md`).
